# CLAUDE.md — `src/usvote/`

Module-specific guidance, moved from the root `CLAUDE.md` (#298). Claude Code loads this file on demand, once a file under this directory is read. The root file's module map and cross-cutting invariants still apply.

## Entry points

**Entry points (unified in #84b, subcommand-based).** Every package `__main__` now dispatches subcommands, and the collision the issue named ("same spelling, different meaning") is **reduced to a documented default, not eliminated**:
- `python -m usvote` — bare stays **EC** (backward-compatible; `--replace` still works bare). Subcommands: `ec` (the explicit bare default) and `all` (the whole-warehouse build — EC + MIT + optional UCSB + optional census + join views, via `usvote/warehouse.py`).
- `python -m usvote.ucsb` — bare stays **snapshot** (the D023 network refresh into `USVOTE_UCSB_HTML_DIR`). Subcommands: `snapshot` (default) and `load` (run `run_ucsb_pipeline`).
- `python -m usvote.mit` — new symmetric `__main__`; single `load` subcommand (default). MIT reads a local CSV, so there is **no** `snapshot` — the source asymmetry is preserved, on purpose.
- `python -m usvote.census` — bare is **load** (#181). Subcommands: `load` (default) and `snapshot` (the D023 network refresh into `USVOTE_CENSUS_CORPUS_DIR`, the only census command that touches the network). It has a network stage like UCSB but takes MIT's default: UCSB's `snapshot` default is backward compatibility for a command that predates its own subcommands, not a principle, so census aligns with the majority and leaves UCSB the documented exception.

So `python -m usvote` loads and `python -m usvote.ucsb` snapshots: the bare spellings still differ across packages (principled — only UCSB has a network stage to snapshot), but each is now a *named default subcommand* rather than an undocumented surprise (D027). `python -m usvote all` is the unified "load everything" front door. Per-source `python -m usvote.mit load` / `python -m usvote.ucsb load` remain the way to load a single PV source (`usvote all` is the only cross-source orchestrator, so there is no top-level `mit`/`ucsb` subcommand — one spelling per action). Both PV `load`s require the EC spine already loaded (they reconcile against `dwh`); run `python -m usvote` (or `all`) first.

## `warehouse.py` — the composition root

`usvote/warehouse.py` is a **composition root** (E6-S3, #84b) — a fifth kind of top-level module, distinct from the `spine.py`/`years.py`/`join.py` EC-domain family. It sequences EC → MIT → (optional) UCSB → (optional) census → view rebuild → the #167 overlap gates (`run_warehouse`; `rebuild_views` is the one place the view ordering is expressed — **four** steps since #184, not three: `build_pv_union → create_ec_pv_views → create_hybrid_views` is the chain, and `create_per_capita_view` follows it as a documented **non-chain** step, depending on nothing the first three produce and **skipping rather than raising** when `dwh.election_population` is absent, which is what keeps a public EC + MIT clone building — D064(e)), and it is the one top-level module that imports *from* every source (EC, both PV subpackages, and census). That does not violate the D015 source-to-source prohibition: a composition root sits **above** both EC and PV, exactly like `__main__`, so it is exempt (D027). The invariant that keeps the exemption honest runs the other way — **nothing under `usvote/{mit,ucsb,pv,census}/` may import `usvote.warehouse`** (a back-import would invert D015 into a cycle), enforced by a test mirroring the greppable `dwh.votes` guard. The warehouse build is **per-source atomic, not globally atomic** (each pipeline owns its own transaction, #84a; the orchestrator opens none): a mid-build failure leaves the committed sources in place, and the honest recovery is `run_warehouse(..., replace=True)` — *not* a bare re-run, which would hit a unique-violation on the first already-loaded source. **That recovery does not apply to a D017 layer-3 breach** (#167): those gates are the *last* step, deliberately, so the warehouse and every view are already built when one fires — `replace=True` rebuilds the same facts and re-hits the same breach. The escape is `--no-validate-overlap` (or `validate_overlap=False`), which exists because gate 1's per-year floor is the threshold D051 says to expect to retune first. Because `run_ec_pipeline(replace=True)` does `DROP SCHEMA dwh CASCADE` (taking the PV tables and views with it), the join views are **always rebuilt** as the final step — `run_warehouse` is what E7/E8 rely on to leave `ec_pv_preferred`/`ec_pv_redistributable` — and, since #124, the four `hybrid_*` views — populated after a `--replace` build. `election_per_capita` rides along on that same last step — `rebuild_views` calls its builder **unconditionally**, and the builder probes for `dwh.election_population` rather than for this build's corpus, so an `all` build with no census corpus still refreshes the view over facts a *previous* census load left behind. Separately, every `python -m usvote.census load` run creates it from `usvote/census/__main__.py` instead, because each entry point's composition layer owns view creation while the shared pipeline stays view-free like its MIT and UCSB siblings (D064(c-bis)) — without which a `--replace` load would `DROP TABLE ... CASCADE` the view away and exit 0, and a plain load would never create it at all.

## Dependency-free EC-domain modules

`usvote/years.py` holds the election-year domain constants (`ec_ingest_years`, `UNSUPPORTED_EC_YEARS`) and is deliberately dependency-free, so a pure transform can derive its year scope from the EC spine without importing the orchestrator (and its DB/network stack). `usvote/pipeline.py` re-exports those names.

`usvote/count_status.py` (#143 / D043 §3, D044; extended in #144 / D046) is the second member of that dependency-free family and exists for the same reason: the `dwh.votes` count-status enum (`counted` / `not_counted` / `disputed`, plus `build_count_status_check`) has **two callers that must not depend on each other** — `transform.py` *assigns* the values, `load.py` builds the `CHECK` from them. Parking the tuple in `transform` would point the DDL builder at the pandas transform module; parking it in `load` would drag psycopg2 into the transform import chain. It is stdlib-only. The CHECK-built-from-a-value-tuple pattern is lifted from `usvote/pv/status.py` (D024 §4), but that module is **not** stdlib-only — it imports numpy and pandas — so the two share the pattern and not the dependency property. The status answers "were these cast votes actually **counted** by Congress?" at the `(year, state, candidate)` grain (D043 §4 — 1872 Georgia counts 8 of its 11 and rejects 3, so a `(year, state)` roster cannot express it), and is deliberately disjoint from `ELECTORAL_VOTE_SHORTFALLS`, which records votes **never cast**; the disjointness is structural, since a cast-then-rejected row still sums to its allotment. #144 added the module's second export, `COUNTED_VOTES_COLUMN` (+ `build_counted_votes_check`), for the same two-callers-that-must-not-depend-on-each-other reason — and it belongs here rather than in `transform.py` because **the enum is its definition**: a row's counted votes are its cast votes when `counted`, else 0.

`usvote/apportionment.py` (#182 / D060) is the third member of that dependency-free family, and the reason it sits at the top level rather than in `usvote/census/` is the same D015 argument that keeps `years.py` there: it is keyed on the **election** year, imports only `usvote.years`, and knows nothing about census population, file layouts or the Bureau — "which apportionment was in force" is an election-domain fact. Inside a source subpackage, the first non-census consumer (a warehouse query, or #183 written as an EC-side reconciliation) would have to import *up* from that subpackage. It holds `governing_census_year` and the materialized `GOVERNING_CENSUS_BY_ELECTION`, and it is **a lookup, never a formula**: a census taken in year *C* is apportioned into the House elected in *C+2*, so it governs presidential elections from *C+2* on — except that Congress failed to pass an apportionment act after the **1920** census, the only such failure, so the 1910 apportionment held a second decade and **elections 1924 and 1928 are governed by 1910** (`NO_APPORTIONMENT_CENSUSES`). The repo's own fact is the oracle: per-state `total_electoral_votes` is identical across 1912–1928 and 32 states move at 1932. Nearest-decade rounding is wrong for 12 of the 51 elections (it maps 2020→2020 where the answer is 2010); a bare decade lag is wrong for 1924/1928. The offline test oracle is a **hand-written 51-year literal**, and the allotment cross-check is an *integration* test because the counts exist only in `dwh.votes` — the committed roster fixture carries none by design (D024 §5). The dependency-free property is enforced, not claimed: an import scan plus a subprocess that imports the module with pandas/psycopg2/requests/geopandas unimportable, with a non-vacuity twin (the first version of that guard used `find_module`, removed in Python 3.12, and was silently inert). Note the semantics it deliberately does **not** carry: `governing_census_year` is the *apportionment* in force, which at 1924/1928 is not the most recently *enumerated* census — so #184's denominator for those two elections is 14-year-old population, named in D060(c) so that stays a choice rather than an accident.

## `spine.py` and `join.py`

`usvote/spine.py` is a fourth kind of thing: **EC-spine readers** (`read_ec_participation`, `read_ec_getters`) that a PV source uses to pull EC facts back out of `dwh.votes`/`dwh.candidate` across a DI seam. It lives at the top level (not under `usvote/pv/`) because it embeds EC-star-schema knowledge — nothing under `usvote/pv/` names `dwh.votes`. Its precedent is `usvote/years.py`: an EC-domain module a PV stage reads *from*.

`usvote/join.py` is the **EC<->PV join seam** (E6-S2, #69 / D026) — another top-level EC-domain module in the `spine.py`/`years.py` family (it names `dwh.votes`/`dwh.candidate`, so the same greppable invariant keeps it out of `usvote/pv/`). It joins a **resolved** PV series onto the EC spine — `pv_preferred` (analysis/E7) or `pv_redistributable` (API/E8), never the raw `dwh.pv_votes` union (D017, else the 1976–2024 overlap fans out 2×) — as an **EC-left join** at the canonical `(year, state, candidate)` grain, exposed as `ec_pv_preferred`/`ec_pv_redistributable`. EC-left is correct because the EC `votes` fact is **dense**: the Archives prints `-` for "no electoral votes here", which the parser reads as `0` (`parse.py`), so a *loser is an explicit 0-EV row, not a missing one* (verified rectangular across all 51 years; ~59% of rows are such 0-rows, now guarded by `transform.assert_rectangular_state_grain`). So the loser rows the thesis needs — "lost the EC, won the PV" — survive the LEFT JOIN with their real EC votes and PV attached; a getter with no PV keeps NULL PV (an honest D005 gap). `national_electoral_votes` is a `SUM(...) OVER (PARTITION BY year, candidate_id)` window (exact on the dense fact), joined since #144 by `national_counted_electoral_votes` (the same window over the counted measure) and the per-row `president_electoral_votes_counted` that coverage policy (c) re-sums over a restricted state set (D046) — both **appended** to `EC_PV_COLUMNS`, never inserted, because `CREATE OR REPLACE VIEW` can only add trailing columns and a mid-list insert breaks `rebuild_views` against any existing warehouse. #139 appended two more for the same reason — `count_status` + `count_status_reason`, the row-grain fact D043 §4 fixes (the view excludes `is_total` rows, the one place D044 says the status must not be read) — and **surfaced all four publicly** (D047/D048). Note the containment property that made that a *deliberate* step rather than an automatic one, and which still holds: `snapshot_schema.DATA_COLUMNS` is an **independent explicit projection**, not derived from this tuple, so adding a column here reaches neither the snapshot nor the content hash until someone lists it there too. The direction is one-way by design (D047 §3) — a test asserts `DATA_COLUMNS ⊆ EC_PV_COLUMNS ∪ derived`, and the reverse assert is forbidden. The one EC-left footgun — a PV row matching no EC row is silently dropped — is caught by a **fact-level anti-join** (`assert_db_pv_matches_ec`) run as a view-creation precondition (the reciprocal guard `docs/canonical-keys.md` describes). (An earlier draft used a FULL OUTER "participant" view on the false premise that the fact was *sparse*; the corrected D026 records why EC-left replaced it.)

## `hybrid.py` — the three-method computation core

`usvote/hybrid.py` is the **three-method computation core** (E7-S2, #121 / D037/D038/D041) — another top-level EC-domain module in the same family (it names `ec_pv_preferred` and `dwh.pv_state_status`, so the same greppable invariant keeps it out of `usvote/pv/`; that invariant is now **enforced** by `tests/unit/test_layering.py`, which also forbids any `usvote/{mit,ucsb,pv,census}/` module importing it). It rolls a **resolved** join view up to per-`(year, candidate)` national outcomes and derives the three method scores: the EC share, the PV share, and the **hybrid** — `(ec_share_hybrid + pv_share) / 2`, the average of the two ratios, highest average wins (D037). Two grains: `build_hybrid_frame` (per candidate) and `build_hybrid_summary` (per election — the three winners, `ec_determinative` and `pv_coverage`, plus, as of #123/E7-S4, the two flips and the three margins). `HYBRID_SUMMARY_COLUMNS` is therefore **twelve** columns, and #123 **appended** its five rather than inserting them — the same `CREATE OR REPLACE VIEW` constraint that governs `EC_PV_COLUMNS` (D047) binds here too as of #124, which materialized the tuple as the `hybrid_summary_preferred` / `hybrid_summary_redistributable` views. The order is held by a **hand-written literal** assert (`TestShape.test_the_summary_column_order_is_pinned_to_a_literal`, the twin of `test_join.py`'s `EC_PV_COLUMNS[:15]` pin), and it has to be a literal: the summary frame is built with `columns=list(HYBRID_SUMMARY_COLUMNS)`, so any assert comparing the frame against the constant is circular and passes under a reorder or a mid-list insert alike — as #123's review proved by monkeypatching it. `HYBRID_CANDIDATE_COLUMNS` gained the equivalent literal pin in #124, where the tuple became a view column contract; both tuples are now append-only, and with `hybrid_summary_*` sitting on top of `hybrid_*` a breaking change needs a `DROP ... CASCADE` migration rather than a `CREATE OR REPLACE`. `pv_flip` / `hybrid_flip` compare each method's winner against the EC baseline (`argmax(ec_share_full)`, the rank-1 leader — **never** `took_office`, which diverges in a contingent election) and are **nullable**: a method with no winner yields NULL, never `false` and — the trap the guard exists for — never `true`, since `_winner` returns a Python `None` rather than `pd.NA` and a bare `!=` would report a flip on every **pre-1976** year when UCSB is absent — MIT still covers 1976–2024, so 13 of the 51 years are unaffected. `ec_margin` / `pv_margin` / `hybrid_margin` are top-2 **percentage-point** gaps (D037) taken over **each method's own non-NULL scores** — necessary, not fastidious, because 4 of the 13 redistributable years carry a candidate with electoral votes and no popular vote (faithless electors; five of 2016's seven rows), so the three top-2 sets genuinely differ within one year. With fewer than two scored candidates a margin is NULL, never `top1 - 0`. `ec_margin` reads the policy-invariant `ec_share_full` so it stays coherent with the `ec_winner` and `ec_determinative` derived from that same column, while `hybrid_margin` tracks `hybrid_score`; the asymmetry is deliberate.

The **EC share is deliberately split in two**, and the split is a safety property (D037/A): `ec_share_full = national_counted_electoral_votes / ec_denominator` is policy-invariant and the **only** input to `ec_determinative`, while the policy-selected `ec_share_hybrid` feeds `hybrid_score` alone. So no coverage policy can manufacture a constitutional majority that never existed. The failure it guards against is the **naive** restriction — trimming 1824's denominator to the popular-vote states while leaving the numerator alone — which reads Jackson at 99/190 = 0.52, over the line, when the real answer is 99/261 = 0.379 and the House decided the election. Policy (c) as implemented does **not** make that mistake (it restricts both halves, giving 84/190 = 0.442), but the split is what makes the mistake unable to matter even if a future policy commits it. `ec_denominator` is the **appointed** allotment (each state's `total_electoral_votes` counted once — a bare aggregate over the joined rows would multiply it by the candidate count), exactly the 12th Amendment's "majority of the whole number of Electors **appointed**", while the numerators are votes **counted** (#144 / D046 — they were votes *cast* until 1872 forced the distinction; both gaps in the appointed ≥ cast ≥ counted ladder are documented, and the switch is strictly safer since a smaller numerator can only shrink a share). Both gaps therefore make candidate EC shares sum to **≤ 1.0, never == 1.0** — 2000 is Bush **271 of 538 appointed** against a **270** threshold, not against the **269** a cast basis (537 ÷ 2, rounded up) would have set — the contrast is between the two *thresholds*, not two tallies of Bush's votes, which are 271 either way (D041); 1872 is Grant **286 of 366 appointed** against the **184** Congress announced, not 286 of the 352 the Archives page itself totals. `president_electoral_rank` moves to the counted basis with it, and the co-switch is mandatory rather than incidental: `assert_ec_winner_matches_rank` compares `argmax(ec_share_full)` against rank 1, so a half-switch would fire it on 1872 alone. No winner and no `ec_determinative` outcome changes across the 51 years — in both anomaly years the EC winner is Grant, whose votes were entirely counted — but 1868 Seymour's `ec_share_full` moves 80/294 → 71/294. `ec_determinative` is `true` only on a **strict** `> 0.5`; `false` means *no EC majority*, a populated and expected state — the hybrid's motivating case — never a null-because-broken.

The **`dwh.pv_state_status` roster is a first-class input**, not a later bolt-on: `EC_PV_COLUMNS` carries `total_electoral_votes` but not `pv_status`, so which states are `legislature_chosen` lives only on the roster, and `pv_coverage` (Σ EV over `popular_vote` states ÷ `ec_denominator` — EV-weighted, D024 §8) **cannot be inferred from a NULL `candidate_votes`**: that would conflate a state where no popular vote ever existed with one the source merely does not cover, the exact distinction D024's no-`unknown` design preserves. The denominator policy is settled at **(b)** (D038) inside `apply_coverage_policy`; #122 adds the `policy` argument and the unshipped (c) branch. The browsable companion is [`docs/pv-coverage.md`](docs/pv-coverage.md) (E7-S6, #125) — what the column measures, why EV-weighted rather than state-count, the **twelve** verified `legislature_chosen` years (1824–1876, both weightings), the 1824 worked example (margin 8.09 → 14.69 pp under (c), winner invariant), and the surface-dependence a display consumer trips over first: those twelve values are the `ec_pv_preferred` numbers, and on the `hybrid_redistributable` **warehouse view** every pre-1976 year reads NULL. **Since #102/D053 that is no longer true of the public API**, whose snapshot derives coverage from the in-repo catalog and so carries the real figure for all 51 years — the view and the artifact diverge on this one column, deliberately. The module **shipped no SQL until #124** (E7-S5 / D050), which materializes it as four views — `hybrid_preferred`/`hybrid_redistributable` at the per-candidate grain and `hybrid_summary_preferred`/`hybrid_summary_redistributable` per election — from one parameterized builder pair, created by `create_hybrid_views` and rebuilt by `warehouse.rebuild_views` after `create_ec_pv_views`. The translation was mechanical because the module was written for it: a view cannot `raise`, so the tie check is a **separate** `assert_no_winner_tie` that becomes a view-creation precondition, and the winner becomes a `row_number() ... DESC NULLS LAST` window. **The SQL implements policy (b) only** — (c) stays Python-reachable, which is what makes the public surface's treatment fixed rather than configurable. The pandas builders are now the **tested oracle** (the `join.py`/`pv/views.py` dual-expression pattern), and the honest limit is worth knowing: `create_hybrid_views` runs the existing guards over the *pandas* side, so a SQL/oracle drift passes all of them — only `tests/integration/test_hybrid_views.py::test_the_live_views_match_the_pandas_oracle` covers it, which is why that test is deliberately **not** corpus-gated while its AC-6 sibling is. One live-corpus finding is baked in: `party` is **resolved by `min`, not required constant**, because MIT (`REPUBLICAN`) and UCSB (`Republican`) spell one party two ways and `pv_preferred` resolves the overlap per key, not per year (D017) — `roll_up_national` is untouched, so the snapshot's rollup and content hash are unaffected. `usvote/snapshot.py`'s `build_national_rollup` **calls** this module's `roll_up_national`, so the national-aggregation derivation is single-sourced (D037/F) — one derivation, two roll-up tables (D029).

## `snapshot.py` — the API serving-store build

`usvote/snapshot.py` is the **API serving-store build** (E8-S1, #94 / D028) — another top-level EC-domain module in the `spine.py`/`years.py`/`join.py`/`warehouse.py` family (it names `ec_pv_redistributable`, so the same greppable invariant keeps it out of `usvote/pv/`). It materializes the `ec_pv_redistributable` join view into a **read-only SQLite snapshot** (`python -m usvote.snapshot`, writing `USVOTE_API_SNAPSHOT_PATH`) that the `usvote/api/` subpackage serves with **no live DB at serve time** — Postgres stays the local source of truth and is read only at build time (D028). The snapshot drops the internal `candidate_id` for a deterministic public `candidate_slug` (`usvote/slug.py`, D006 / `docs/canonical-keys.md`), is versioned by a content hash (not a timestamp), and is guaranteed redistributable-only at the source (D030). The serving contract (its five tables — `ec_pv`, `national_rollup`, `hybrid_summary`, `per_capita`, `snapshot_meta`) is documented in [`docs/api-snapshot.md`](docs/api-snapshot.md). `usvote/snapshot_schema.py` holds just the *contract* — table/column names, `SnapshotMeta`, the schema version — and is deliberately **stdlib-only** (no pandas/DB) so both the build side and the serving side can import it across the D028 boundary.

**The served window is the full EC span, 1824–2024** (#139 / D048; it was the MIT-only 1976–2024 until then — the rows were always in the EC-left view, and `build_snapshot` filtered them away). Two windows now live in `snapshot_meta` — `year_min`/`year_max` served, `pv_year_min`/`pv_year_max` popular vote — because coverage must be *stated*, not inferred from a field of nulls. The widening is one deleted filter; almost all of #139 is the honesty scaffolding around it. Every fact row carries a **`pv_status`** (`NOT NULL`) so a null popular vote is never bare — 1860 South Carolina (`legislature_chosen`) and 1860 New York (`popular_vote`) both read null, and the two nulls mean different things. Critically, that status is derived **in-process from `usvote/pv/absences.py` over the EC spine and never from `dwh.pv_state_status`**, whose pre-1976 rows are UCSB-derived (D022) — so no UCSB-provenanced value is on the public path and D030 stays structural rather than becoming an authorized crossing; `tests/unit/test_layering.py` proves it by importing `usvote.snapshot` in a subprocess where `usvote.ucsb` is unimportable. Because the roster derives over the whole `ec_ingest_years()` span and raises on a short warehouse, **a scoped warehouse can no longer build a snapshot** — a deliberate trade that retired `SnapshotMeta`'s old scoped-subset promise. D047's plumbing lands here too: `count_status` + both counted measures are surfaced (else the API would report Grant at 300 in 1872 with no way to see 14 votes were refused), `national_rollup` gains the **appointed denominator** so a counted total is checkable at all (286 *of 366*), and provenance became **heterogeneous** — `ec_source`/`ec_license` (NARA / US-PD) beside the MIT/CC0 pair, since most of the widened table is Archives data and a `meta` block naming only MIT would claim MIT covers 1824. `count_status_reason` is the one free-text column that ships, and only because it is Archives prose from a **closed three-sentence vocabulary** the build pins it to — the same guard shape as the `pv_status` enum. `SNAPSHOT_SCHEMA_VERSION` is **4** (3 → 4 in #245), so a snapshot and the image serving it must cut over together (D034).

**The three-method comparison ships on the public surface** (#102 / E8-S8 / D053 — the last E8 story). `national_rollup` gains the five per-candidate hybrid fields (`ec_share_full`, `pv_share`, `ec_share_hybrid`, `pv_coverage`, `hybrid_score`) and a new **`hybrid_summary`** table carries the per-**election** grain — three winners (each with its public slug), two flip booleans, three top-2 margins in percentage points, `ec_determinative` and `ec_denominator`. Both `/v1/elections/{year}` and `/v1/elections/{year}/summary` return it as a single `election` key; the multi-year state and candidate routes get nothing, having no single election to summarize. **The snapshot recomputes the hybrid rather than reading `hybrid_redistributable`**, which is what D039 originally specified: it calls `hybrid.build_hybrid_from_frames` on the two frames `build_snapshot` already holds — the join frame and the **curated** roster — so it adds no DB read, keeps `build_snapshot` a pure frame function, and discharges D048's action item that `pv_coverage` resolve to the in-repo catalog rather than the UCSB-inclusive `dwh.pv_state_status`. The consequence is **one intended divergence and exactly one**: pre-1976 the warehouse view reads NULL `pv_coverage` (its roster read is scoped to the sources the view carries, and MIT's roster starts at 1976) while the snapshot reads the real figure (1824 = 190/261 ≈ 0.728). Nothing else differs — under policy (b) `pv_coverage` feeds no score, so every share, winner, flip and margin matches the view, which `tests/integration/test_snapshot_build.py` pins on 2000/2016 while asserting the 1824 divergence is still there. `build_hybrid_from_frames` is an **extraction** from `build_hybrid_from_db`, not a new derivation, so the snapshot path inherits the same four guards — above all `assert_no_winner_tie`, since `build_hybrid_summary` deliberately does not raise on a tie (a view cannot `raise`, so #124 split it out) and an unguarded second path would have shipped an arbitrary winner on a dead heat. Note the containment that still holds: `snapshot_schema`'s `HYBRID_SUMMARY_COLUMNS` is an **independent explicit projection** of `hybrid.HYBRID_SUMMARY_COLUMNS`, not an alias — the same one-way rule D047 §3 sets for `DATA_COLUMNS`.

**The per-capita series ships too** (#245 / D069). A fifth snapshot table, `per_capita`, keyed `(year, state)`, carries `dwh.election_per_capita` (`election_year` renamed `year`, `state_usps` joined as for `ec_pv`) and is served at `/v1/elections/{year}/per-capita` and `/v1/states/{usps}/per-capita`; `API_VERSION` is **0.5.0**. Three things changed with it. **(1) Census is a required snapshot input** — `read_per_capita` fails loud when the view is absent, so a public EC + MIT clone builds a warehouse but not a snapshot. That is acceptable because the census corpus is public domain and fetchable; UCSB stays **never** required, since its absence is a licensing firewall (D022/D030), not a convenience. **(2) The view is read by SQL name, not by import**, because `test_no_top_level_module_imports_a_source_subpackage` forbids `snapshot.py` importing `usvote.census` (the same guard that put `per_capita.py` under census, D064(f)). The view name and columns are local literals in `snapshot.py`, the three closed vocabularies (`coverage`, `boundary_basis`, `population_series`) are copies in stdlib-only `snapshot_schema.py`, and `TestPerCapitaContract` in `tests/unit/test_snapshot.py` pins every copy to its census original. **(3) The content hash covers `ec_pv` and `per_capita`** — every `per_capita` column but the ratio — and still excludes the derived tables (`national_rollup`, `hybrid_summary`). `per_capita` is a second source's numbers, not a derivation, so a census reload must move `snapshot_version` or the D034 cutover never fires; the ratio is left out to keep the hash float-free, and the build refuses a ratio that is not `population / total_electoral_votes`, so a change to the view's formula fails the build rather than drifting. The build also guards the table against `ec_pv` in both directions of the key set and on every row's `total_electoral_votes` (a stale census load that keeps every key but carries an old allotment is #243's Nevada 1864 shape). Provenance is now **three** sources: `census_source`/`census_license` = USCB / US-PD sit on `snapshot_meta` and every response's `meta.provenance` beside the NARA and MIT pairs.
