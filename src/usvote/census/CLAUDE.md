Module-specific guidance, moved from the root `CLAUDE.md` (#298). Claude Code loads this file on demand, once a file under this directory is read. The root file's module map and cross-cutting invariants still apply.

## The census source

**A third source subpackage, and the first that is not a popular vote** — `usvote/census/` (E10-S2, #181 / D059) ingests US decennial state **resident** population, 1790–2020, from the Census Bureau's own published XLSX tables into `dwh.census_population`. It conforms to no `usvote/pv/` contract, writes no `dwh.pv_votes` and takes no part in the D017 resolution views — it borrows the *structure* of the PV subpackages, not their schema. Its stages are `scrape` (the D023 corpus, keyed by **logical source id** rather than year so #183's seats files drop in as new keys) / `parse` (the repo's first XLSX reading, stdlib `zipfile` + `xml.etree`, no new dependency) / `transform` / `conform` (#182 — the crossing to *election* grain) / `schema` / `load` / `pipeline`, plus three modules that are **not** pipeline stages — `per_capita` (#184, the view builder: each entry point's composition layer creates the view, D064(c-bis)) and `reconcile` + `seats` (#183, the apportionment guard and its curated constant, described below) — over a dependency-free `sources.py` — the single catalog of each file's URL, filename and **vintage**, which both the fetch stage and the pure transform read so the two cannot drift (a rename used to update the download and silently falsify every row's `source_file` provenance). Three of its four source hazards produce **plausible wrong numbers rather than load errors**, so each is answered by something visible: the two-file **stitch** is a constant (each census comes from exactly one file), the **vintage** is a per-row column (the two tabulations disagree by amounts no assert catches), and the boundary **`basis`** is a per-row label — `present_day` as published, `as_enumerated` where restated. That last is the D005 problem in a new place: pre-1863 Virginia is reported on its modern footprint and so omits the West Virginia counties, understating its per-capita denominator by 12.7%–21.3% across the ten elections 1824–1860. The same restated rows also carried **Alexandria County** (District of Columbia 1801–1846), so for the 1800–1840 censuses the label was false on a second axis until **#251 (D067)** subtracted it: `apply_alexandria_retrocession` runs as a separate step after the West Virginia restatement, from the five figures in `transform.ALEXANDRIA_RETROCESSION` (four as Virginia Note 2 prints them, 1810 corrected from a misprint against the published `Arlington` row). `VIRGINIA_VERIFICATION` records how each census's figure is established — `published_total` (1790/1850/1860), `published_components` (1800–1840), or absent, meaning unverified. The consequence is deliberate and stated in D067(e): the District's row already excludes Alexandria, so **for 1800–1840 Alexandria's people are in no row of `dwh.census_population`**. The table was never sum-consistent (the West Virginia double count is deliberate) and no guard asserts a per-year sum. The correction is applied **in place** with `basis` as a label rather than as part of the key, because a second row per key would recreate the D017 fan-out hazard for every consumer that forgot to filter it. Note that `per_capita.py` lives **here rather than at the top level beside `join.py`/`hybrid.py`**, reversing #184's own approved plan (D064(f)): the view must name `dwh.election_population` and its column contract, both of which are census's, and `test_no_top_level_module_imports_a_source_subpackage` forbids exactly that import from every top-level module but the two composition roots. What makes the census home legal is that the layering guard — `test_no_lower_subpackage_names_the_ec_votes_fact_in_code`, which scans `pv` and `census` — looks for `dwh.votes` **in code only**: it runs `code_only()` first, an AST pass that strips docstrings and comments precisely so the guard does not punish accurate cross-layer prose. No *code* under `usvote/census/` names the fact; the appointed allotment arrives as a *column* on `election_population`. **D064(f) calls this "a literal scan", and that wording should not be carried further** — `per_capita.py`, `conform.py` and `reconcile.py` all name `dwh.votes` in prose and pass, so a contributor who reimplemented the guard as a grep would turn three census modules red.

**#182 (E10-S3 / D060) added the stage that crosses to *election* grain**, which is where three more silent-wrongness classes live. `usvote/census/conform.py` builds a `(election_year, state)` frame — **spine-left**, so the population source never votes on statehood — and runs six guards as one seam (`assert_conforms_to_spine`; the list lives in `build_and_validate_election_population`, and its docstring says which guards can fail on data and which only guard the builder) **before** the write, so a failure leaves nothing written. Its contract `ELECTION_POPULATION_COLUMNS` is append-only and literal-pinned (#183 and #184 both inherit it; it carries `total_electoral_votes` because the appointed allotment is already in the injected participation frame). Three findings shaped it, each a plausible wrong number rather than an error. **(1)** The boundary restatement #181 applies is **correct for 1824–1860 as to the West Virginia counties, and wrong for 1864/1868**: those elections are still governed by the 1860 census, but West Virginia is a separate state holding 5 electoral votes by then, so restated Virginia double-counts its 376,688 people. `BOUNDARY_SUCCESSIONS` restores the published `1,219,630` and the pin is an **independent literal** that *checks* `apply_virginia_boundary_correction` rather than inheriting it — necessary because, `basis` being out of the natural key (D059), the published figure is **not recoverable from the table** (which corrects a claim D059 and `census/schema.py` both made). Virginia is zero-EV in both years, so the defect is latent per-state and live for any **aggregate**. **Read that qualifier as load-bearing rather than as hedging** (#253/D066): the claim is true on the West Virginia axis, which is finding (1)'s whole subject, but those same restated figures also carry **Alexandria County** — District of Columbia from 1801 until its retrocession to Virginia on 7 September 1846 — so for the six elections **1824–1844** they were 0.79%–0.91% high and were *not* the borders-at-election figures. That is a different mechanism (1846, DC→VA) from this one (1863, VA→WV). **#251 (D067) corrected it at census grain**, which moved those six election rows down, and so created the one election where the correction is wrong: 1848 is governed by the 1840 census but held after the retrocession. `BOUNDARY_RETROCESSIONS`, built from the same constant, adds Alexandria back through `apply_boundary_retrocessions` for that **derived** reversal set (elections whose governing census predates the retrocession while the election follows it — {1848} on today's spine, and never listed as years); 1848 keeps 1,249,764, reached by a different route. `Retrocession` is a separate shape from `BoundarySuccession`, not an entry in it, because it is a recipient *gaining* territory from a jurisdiction that may hold no row. Two guards came with it. `assert_boundary_corrections_disjoint` runs first and refuses a succession and a retrocession of one state that share a census or an election. `assert_retrocession_restored` pins the reversal's footprint and is **a consistency check, not a verification**: the District does not vote in 1848 and both sides read one constant, so there is nothing independent to check it against. `assert_no_interpolated_population` admits the reversal keyed on **`(election_year, state)`**, not on the census, because 1840 governs both 1844 and 1848 and only 1848 may carry the added-back figure. **(2)** `boundary_basis` is its own election-grain vocabulary (`at_election` / `present_day`), *not* the census `basis`, because for 1864 Virginia the **published** figure is the borders-at-election one — reusing the census label would stamp an honesty warning on the correct number. **(3)** Of all **2,204** participating `(election_year, state)` pairs across the 51 elections (1,898 checked against `tabs15-65.xlsx`, the other 306 — elections 2004–2024 — against the population-change table), **three** had no governing-census figure, in **two kinds** that must not be collapsed: `(1848, Texas)` is `absent_from_source` (the Republic of Texas was not enumerated by the US in 1840 — the figure cannot exist, and 4 electoral votes ride on it), while `(1960, Alaska)` and `(1960, Hawaii)` were `present_but_unparsed` (128,643 and 499,794 *are* published, in a transposed second table the parser did not read — a defect here rather than a fact about history). **#234 (D061) retired those two**, teaching `parse_resident_1790_1990` to read that table — detected by its `Race` label column, which across all 51 sheets selects exactly those two, pinned by a corpus-gated `TestRealCorpus` in `tests/unit/test_census_parse.py` that skips without `USVOTE_CENSUS_CORPUS_DIR`. The label column is preferred over any cell-shape rule because a four-digit population is indistinguishable from a year; **how much weaker the shape rules are lives in that test and is deliberately not paraphrased anywhere**, since two successive attempts to state those counts in prose both stated them wrongly — D061 records what each got wrong, the second being a rule that reads as vacuously true and so selects all 51. **D062 supersedes D060's now-false catalog paragraph and its discharged Action-required section** — the log is append-only and D060 is no longer its newest entry, so the correction is a new record rather than an edit. Alaska now reaches 1880 and Hawaii 1900; their differing year-header columns (B against C, with B empty) are why the column→year map is read from the header rather than hardcoded, and Hawaii's sheet joined the committed fixture as the only offline witness to that. Alaska's off-cycle 1939/1929 censuses are **emitted faithfully and dropped by `SOURCE_SPANS`**, never relabelled (D005) — the scope decision staying in the transform is what makes "skipped" and "relabelled-then-deduped" distinguishable. The catalog is now one row; the `present_but_unparsed` *kind* stays defined with no member. `assert_spine_states_covered` is two-way, and the direction with teeth is the second: a *declared* exception for a cell that turns out covered is a false claim in `docs/corrections.md` that nothing else would notice. Completeness is provable only over all 51 sheets, so `TestRealCorpus` skips unless `USVOTE_CENSUS_CORPUS_DIR` is set. #182 also fixed a one-figure silent parse loss — South Carolina 1790 = 249,073, whose row label uses U+2026 ellipsis leaders the year regex rejected, dropping the row entirely.

**#183 (E10-S4 / D063) is the epic's strongest validation, and it found a defect in the *electoral record* rather than in the census.** `usvote/census/reconcile.py` checks, for every one of the **2,204** participating `(election_year, state)` pairs, that the published apportionment explains the recorded allotment: `seats + 2` senators, with the District of Columbia answered from the Twenty-third Amendment (3 from 1964) since it is `(X)` in every apportionment table and apportioned from no census. Reconciling raw seats is off by exactly 2 for every state in every year, which reads as a data problem rather than an arithmetic one — that is the wrong-easy-answer the story was filed to name. **The seats are curated in `usvote/census/seats.py`, not parsed** (D063): the full-span source is a two-page text-layer PDF, and a runtime parse would put `poppler-utils` — a system binary, unpinnable in `uv.lock` — on the CI critical path of the one package whose parse stage exists to avoid a dependency. `scripts/extract_census_seats.py` renders the published table for comparison (it writes no file, and its raw output is deliberately not the constant: it emits five census years the constant omits and cannot emit 2020 at all), and a corpus-gated `TestRealCorpus` compares all **969** PDF-sourced cells, skipping without `USVOTE_CENSUS_CORPUS_DIR`. Because the guard reads only the injected spine and that constant, **`warehouse.run_warehouse` calls it outside the `census_corpus_dir` branch** — the first revision wired it only inside the census pipeline while four prose sites claimed otherwise, so it fired exactly when a corpus happened to exist. **Three kinds of disagreement**, catalogued in [`docs/corrections.md`](../../../docs/corrections.md) with statutory citations (per-kind counts pinned by `TestTheCatalog.test_the_entries_per_kind`): 14 `electoral_votes_withheld` (1864 and 1868 only — 1872 has none, a finding rather than a silence, and Georgia 1868 is absent because its votes were `disputed` under D044 while its allotment was intact), 2 `seats_not_apportioned` (West Virginia 1864/1868, admitted after the 1860 apportionment — the case a one-sided guard passes in silence), and `electoral_record_understates_allotment`, which is **defined with no member** on the D061 `present_but_unparsed` precedent. Its one member was `(1864, Nevada)`, where the Archives print a **cast** 2 in a column D041 defines as **appointed** (admitted eight days before the election, Nevada appointed three electors and two voted — the appointed-exceeds-cast case of 1832 Maryland and 2000 DC, differing only in which figure the table prints). **#243 (D068) corrected it in the spine** and removed the entry, as its self-cleaning design required: `(1864, "Nevada"): 3` in `APPOINTED_ELECTORS_NOT_IN_TABLE` and `(1864, "Nevada"): 1` in `ELECTORAL_VOTE_SHORTFALLS`, each paired with the other through `assert_row_votes_sum_to_total`, so 1864's `ec_denominator` is 234 rather than the page's printed 233. That made `APPOINTED_ELECTORS_NOT_IN_TABLE` cover **two** ways the table understates an allotment — printing `-` (1872 Arkansas and Louisiana) or printing the cast figure — with values that stay the absolute appointed allotment. Two transform guards changed with it: `assert_corrections_reconcile_printed_totals` subtracts each corrected state's **printed** allotment (a snapshot `_printed_state_allotments` takes before the correction runs), and `_apply_appointed_elector_corrections` refuses a value at or below what the source prints, so that constant is now self-cleaning too. A seat cell has **three** states, not two — a digit, an explicit `(X)`, and an **absent key**, which fails unconditionally, because collapsing the last two would let a curation omission pass as a declared exception. The direction with teeth is the stale-declaration reciprocal, not a reverse scan: on a dense spine (D026) both historical kinds are caught by iterating the electoral record, and a reverse guard written for that purpose turned out to compare two derivations of the same call and was removed.

**D066 (#253) settles what a per-capita *denominator* means, and it is the one census decision that spans three stories.** A per-capita denominator uses the **borders in force at the election** — that governs `dwh.election_population` and the `dwh.election_per_capita` view. The ruling exists because **vintage, footprint and denominator provenance are three independent axes, not two**: which census supplies the figure (`governing_census_year` — an apportionment fact), which territory that figure describes (`boundary_basis` — the axis D066 rules on), and where `total_electoral_votes` came from (an apportionment artifact). The opposing case is that axis 3 is apportionment-derived so axis 2 should be; the reply is that axes 1 and 3 ask *whose allotment is this* while axis 2 asks *whose people are these*. The deciding argument is structural rather than aesthetic: apportionment basis is **not consistently implementable at election grain** — the frame is spine-left, so under that basis Virginia's West Virginia counties sit in two rows of one 1864 frame, and West Virginia's own 1864 footprint is **undefined**, its 5 electoral votes coming from the admission act rather than from the 1860 apportionment. So `usvote/census/reconcile.py` is **untouched and correctly on the apportionment basis** — both sides of its equality are apportionment artifacts, which makes seat reconciliation an apportionment question end to end. Two surfaces in one repo legitimately sit on different bases because they ask different questions. **The criterion is not the label, and the ruling relabels nothing** (D066(e)): the Virginia rows for 1824–1844 kept `at_election` while they were still high, rather than taking `present_day`, which asserts only *"not established"* about rows whose defect was established and quantified. D066 left the grain of the fix open; **D067 (#251) chose census grain plus an election-grain reversal for 1848** (described under #182 above), which makes those six labels true and retires the interim third state D066(e) allowed. `boundary_basis` is two-valued in practice as well as in its CHECK.

## Data model: the census tables

- **`census_population`** — PK `population_id`; `census_year`, `state` (FK → `state`), `series` (CHECK, one value `resident`), `basis` (CHECK — `present_day` / `as_enumerated`), `population` (**`integer`, never `smallint`** — state populations reach ~39M and the EC fact's vote-measure reflex overflows at 32,767), `vintage` + `source_file` (which published tabulation and which file the row came from), `redistributable` (D014, uniformly `true` — a conscious departure from D017's move of that flag off the per-row fact, recorded in D059), `note`. Natural key `(source, census_year, state, series)`; `basis` is deliberately **not** in it (#181 / D059). For 1800–1840, Alexandria County's people are in **no** row: Virginia's rows are `as_enumerated` without it and the District's rows, as published, already exclude it (D067(e)).
- **`election_population`** — PK `election_population_id`; the **election-grain** frame #182 built and #184 persists (D064(a)). Grain and natural key are the same thing, `UNIQUE (election_year, state)` (`state` FK → `state`) — one row per *participating* pair, built spine-left so the population source never votes on statehood. `governing_census_year` (which apportionment-era census supplies the figure — `usvote/apportionment.py`), `total_electoral_votes` (**`not null`**, the appointed allotment read off the EC fact), `population` + `population_series` (**nullable together**, never one without the other — the two-way coupling `assert_election_population_shape` enforces, since a series label beside an absent figure asserts the provenance of a value that does not exist), `boundary_basis` (CHECK — `at_election` / `present_day`, its **own** election-grain vocabulary, *not* the census `basis`, D060/D066), `coverage` (CHECK — `covered` / `no_governing_figure`: the column that says *why* a population is absent).
  `total_electoral_votes` being `not null` is a load-bearing premise, not a formality (D064(c)): the `dwh.election_per_capita` view divides `population::double precision / NULLIF(total_electoral_votes, 0)`, so widening that column would pass a NULL straight through and break the honest-gap promise with no change to `per_capita.py`. That promise is why there is **no `per_capita_status` column** — the ratio's two NULL causes are readable off the row's own operands (a null `population`, or a zero `total_electoral_votes`), and a status column would be derived from two of its own neighbours. The view reaches the public API through the snapshot's `per_capita` table — shipped in #245 (D069), described under `usvote/snapshot.py` in [`src/usvote/CLAUDE.md`](../CLAUDE.md). As merged, the 2,204 participating pairs are 2,189 computed + 1 `no_governing_figure` (`(1848, Texas)`) + 14 zero-allotment (11 states in 1864, 3 in 1868).
