### `CODE_REVIEW` — the code-review gate is `/code-review`, and **not** these three

Three neighbouring commands are easy to reach for by mistake. Only the first satisfies the gate:

- ✅ **`/code-review`** — the bug-hunting review of the working diff. **This is `CODE_REVIEW`.**
  Run it on the PR branch once the PR is open, address viable findings, and land them as the
  repo's conventional `Address code-review findings on X (#NN)` follow-up commit.
- ❌ **`/review <PR#>`** — reviews a *GitHub PR*. Useful, and past iterations journaled it in this
  slot, but it is a different tool with a different scope (the PR as published, not your working
  diff) and it does **not** discharge the gate. If a run uses it, say so explicitly in the journal
  rather than recording it as `CODE_REVIEW`.
- ❌ **`/simplify`** — quality only (reuse / simplification / efficiency / altitude). It states
  outright that it does not hunt for correctness bugs, which is exactly what this gate is for.
  Optional extra polish, never a substitute.
- ❌ **`/code-review ultra`** — the multi-agent cloud review. It is **user-triggered and billed**;
  the loop cannot launch it. Recommend it to the human for a high-stakes branch instead.

## 2. `ARCHITECT_TRIGGERS`

**These triggers govern the plan-informing use only, and the list below does not bound
`DESIGN_AGENT`.** The engine consults that agent for a scope ruling whenever a BLOCKING code-review
finding raises a design question — on every route, at whatever round it arises, and stopping with
that ruling. Nothing in this file turns that off.

Fire `DESIGN_AGENT` (`architect`) when a plan touches any of the following; bias toward calling it.

- **Shared/cross-source contracts:** anything under `usvote/pv/` (the `schema.py` record shape,
  `status.py` roster/enum, `pv/load.py` write seams), or the `dwh` DDL / star-schema grain.
- **Source-namespacing boundary (D006/D015/D027):** a new top-level EC-domain module, a new PV
  subpackage stage, or any change to the composition root (`usvote/warehouse.py`) or the
  `spine.py`/`years.py`/`join.py` family. The greppable invariant (nothing under `usvote/{mit,ucsb,pv}/`
  imports `usvote.warehouse`; nothing under `usvote/pv/` names `dwh.votes`) must not regress.
- **The EC↔PV join seam (D017/D026):** changes to `join.py`, the `ec_pv_preferred` /
  `ec_pv_redistributable` views, or the EC-left / dense-fact assumptions.
- **The API serving boundary (D028/D031):** the snapshot contract (`snapshot_schema.py`,
  `docs/api-snapshot.md`), the `usvote/api/` import graph ("no live DB at serve time"), or any new
  `/v1` endpoint / response envelope.
- **A new historical data correction or PV source**, or when the orchestrator is unsure.
- **Reader-facing wording** (anything on root `CLAUDE.md`'s *Who writes wording* list) does not
  fire `DESIGN_AGENT` on its own; it owes §6's wording spec instead.
- **Skip** for docs-only, comment/typo, and pure test-addition changes — **unless the test is the
  only acceptance guard for a shipped public contract**, in which case the architect runs, and
  reviews what the test asserts *and fails to assert*. The contracts that qualify: the snapshot /
  API serving contract (`snapshot_schema.py`, `docs/api-snapshot.md`, `usvote/api/`), the EC↔PV
  join seam (`join.py`, the `ec_pv_*` views), and the D022/D030 licensing firewall
  (`tests/unit/test_layering.py`'s UCSB-unimportable subprocess guards, and
  `test_no_fixture_ships_real_ucsb_bytes`). The discriminator generalizes past that list —
  **"if this test is wrong, what notices?"** — and when the honest answer is "nothing", the design
  question is live whatever directory the diff sits in. Deliberately narrow: it does **not** fire
  for a coverage top-up, a regression test alongside a bug fix, or a test on an already-guarded
  surface. Motivated by #150 (`tests/integration/test_snapshot_build.py`), where the skip was
  defensible by the letter and wrong by the spirit — the overridden architect pass found the
  guard's headline assertion **circular**: it compared the artifact's `pv_status` against the very
  catalog the artifact derives that column from, so a wrong entry moved both sides together and
  nothing went red.

## 4. Security routing

> All rules here are GitHub/host-specific. Host **is** GitHub. No dedicated security workflow
> exists yet — none of the workflows in `.github/workflows/` is one — so routing is via the
> built-in `/security-review`.

- **`.claude/`-only change** → run local `/security-review` (no CI security workflow to trigger).
  **This rule wins over the "Skip for docs / no-surface changes" bullet below**, which it would
  otherwise tie with on every such change — `.claude/` carries hook and permission config, so a
  no-surface *diff* is not a no-consequence one.
- **Sensitive surface** → run `/security-review` when dev-complete. **Six** path surfaces, plus
  one change-shaped trigger:
  - **API serve layer** — `usvote/api/`, plus `usvote/snapshot.py`: it builds the artifact that
    layer serves, and its `assert_redistributable_only` is the single gate keeping
    non-redistributable UCSB-derived rows (D022/D030) off the public surface. A path rule, not
    the interpolation trigger below, because that trigger fires on *new* interpolation and this
    module already interpolates.
  - **Deploy / CI automation** — `.github/workflows/**`, `deploy/`, `Dockerfile`. This is the
    most privileged code in the repo and, until #247, it matched no rule at all: `deploy.yml`
    holds `id-token: write` and the Cloudflare token/zone secrets, and `deploy/killswitch/`
    is authorized to change the live service's `max_instance_count`. Enumerated, and found by
    #248's review one axis over from the omission #247 was filed about.
  - **Public dashboard** — all of `dashboard/`. Decided 2026-09-30 (#290), on four grounds, any
    one of which would be enough. It is a **deploy root**: `.gcloudignore` decides what reaches
    App Engine, so a file added there ships. `app.yaml` **names the runtime service account**
    (`explore-run@uspv-explore`) and the instance cap that is also the cost cap. `explore/api.py`'s
    `fetch` is the **D070(b) chokepoint** — the one function that opens a connection, which is
    what keeps the dashboard off `run.app` and off the origin secret. And it is the repo's only
    hand-written code that **builds HTML from a request**: #277's first review round found a
    live reflected XSS there, fixed before merge. Its deploy workflow, `.github/workflows/deploy-dashboard.yml`, was already
    covered by the pattern above and needs no rule of its own. The guards that pin these
    properties (`tests/unit/test_dashboard_guards.py`) are deliberately **not** listed: a
    change that weakens one is §2's question ("if this test is wrong, what notices?"), not a
    security path.
  - **Corpus integrity** — `usvote/corpus.py`: the sha256/manifest provenance code all three
    snapshot stages share. It was extracted *out from under* the `scrape.py` name, so the
    pattern below no longer reaches it — the same migration-out-from-under-a-rule failure this
    section diagnoses.
  - **DB write/connection path** — `usvote/db.py`, plus **any `load.py` anywhere under
    `usvote/`** (`usvote/**/load.py`, the `**` matching zero directories too; today that is
    `usvote/load.py`, `usvote/pv/load.py`, `usvote/census/load.py` — MIT and UCSB have none,
    they write through `usvote/pv/load.py`).
  - **Scraping/network** — **any `scrape.py` anywhere under `usvote/`** (`usvote/**/scrape.py`;
    today `usvote/scrape.py`, `usvote/ucsb/scrape.py`, `usvote/census/scrape.py`).
  - **Also fires** when a change introduces a *new* module that builds SQL/DDL by string
    interpolation, or a new interpolated identifier or value in an existing one. Keyed on the
    change rather than on a path, deliberately: the modules this would otherwise enumerate are
    the **view builders** (`join.py`, `hybrid.py`, `census/per_capita.py`), which read rather
    than write and whose ordinary edits are column and ordering work — gating every one of those
    is over-gating. `load.py` is *also* interpolating DDL and *is* gated on every touch, and that
    is not an inconsistency: it is gated for being a write path, which a view builder is not.

  **Enumerated paths or a pattern? Both, on a stated rule — pattern where a stage name repeats
  across subpackages, enumeration where it does not.** Decided 2026-09-19 (#247). The previous
  list was all-enumerated and went stale by omission: `usvote/census/` was created with a
  `load.py` (new DDL + an insert path) and a `scrape.py` (a real network stage,
  `python -m usvote.census snapshot`), and **#184's delta matched none of the list** — the gate
  ran on that PR because the orchestrator applied the engine's over-gating default, not because
  a rule selected it. A rule that depends on someone choosing to over-gate is not a rule.
  Enumeration is more precise and more auditable, and it stays for the surfaces that have no
  repeating axis (`usvote/api/`, `usvote/db.py`) — nothing there is self-maintaining to be, and
  a pattern would only blur it. But `load.py` / `scrape.py` are **per-source stage names the
  source-namespacing convention (D015/D027) grows a fresh copy of with every new subpackage**,
  so that is exactly the axis enumeration cannot keep up with; a pattern there would have
  covered `usvote/census/` on the day it was created, and covers the next subpackage on its.
  The next subpackage is the test of this choice either way.

  Note the repo's own guardrails: no UCSB bytes ever committed (public repo, D022), snapshot is
  redistributable-only at the source (D030), and the wheel uses `packages=` not `force-include`
  (avoids bundling secrets — see `pyproject.toml`).
- **Skip** for docs / no-surface changes.
- **Decided: security review stays purely local** via `/security-review`. No `needs-security-review`

## 6. Reader-facing wording: the `ba` label spec

**Root `CLAUDE.md`, "Working conventions" → *Who writes wording*, is the single source** for what
counts as reader-facing output and who owns its wording. This section links to that list rather than restating it, and
binds the loop to it. The engine has no wording gate, so these rules ride
on steps it already runs: the plan, the human plan gate, implementation, code review and the merge
gate. Ported 2026-10-15 (#369) from claude-hook-validator's §6 as its #46 left it, which closed four
ways the first version could fail quietly.

- **When it's due.** On any route, when the plan adds or changes anything on that list. It goes by
  what the plan changes, not by route or path: a `code` row that adds one help-text constant owes it,
  and so does a `docs` row that edits shipped wording. Unsure ⇒ it's due.
- **At the plan step, `ba` returns text only.** While drafting the plan, invoke the `ba` agent
  (user-global, `~/.claude/agents/ba.md`) with the issue, its comments (`gh issue view --comments`)
  and the planned output. It returns a label spec (a table of key, wording, glossary term and reason)
  and, where needed, the `docs/glossary.md` entries and `## Key index` rows to add or change, as
  text. **It edits no file at this step:** the iteration's branch doesn't exist yet, and the owner
  hasn't approved the wording. Put the spec in the plan under `## Wording spec`, and the glossary
  delta under it.
- **Every plan opens with a plain value line from `ba`** (owner decision on #369, 2026-10-15,
  matching claude-hook-validator's on its #46). At the plan step, on every iteration whether or not
  a wording spec is due, `ba` returns one plain sentence for the plan's `## Value framing`: who
  benefits, and what they can now do or no longer have to do, in glossary terms. It goes first in
  that section, above the orchestrator's own framing, so `/pr-brief` has a line a non-engineer can
  read for its "Value delivered" section and its record's `value.who` and `value.one_line`. When a
  wording spec is due, one `ba` call returns both. If `ba` can't be invoked or returns no line,
  journal `- gate-error: wording-spec — ba — <reason>` and stop for the human, as for the spec.
- **Check that `ba` wrote nothing in this repo.** Telling it to return text is only an instruction:
  its write guard (`~/.claude/agents/ba/guard-writes.sh`) lets it write any file named
  `glossary.md` outside `~/.claude/`, and its own memory directory, and `PERMISSION_POSTURE` says
  delegated agents never write. So the prompt says "return the glossary delta as text; edit no
  file", and around each call the orchestrator runs two checks from the repo root:
  - `git status --porcelain --untracked-files=all`, before and after. The tree is clean at the plan
    step (the ledger is gitignored), so both runs must print nothing.
  - `touch` a marker file in the scratchpad just before the call, and after it run
    `find . -name glossary.md -newer <marker>`, which must print nothing. This one sees gitignored
    paths too (`.claude/loop/`, `.venv/`), which `git status` doesn't.

  Anything either prints is a finding: restore each path (`git restore <path>` for a tracked file,
  delete a file `ba` created), keep only the text `ba` returned, and record it on the
  `- Wording-spec:` line. **The checks don't reach outside the repo**: a `glossary.md` elsewhere (a
  sibling repo's, a temporary copy's) or `ba`'s memory directory goes unseen. If the tree isn't clean
  before the call, don't call `ba`: journal
  `- gate-error: wording-spec — git status — tree not clean before ba` and stop for the human.
- **A wording spec always stops at the plan gate.** Every ledger here runs `plan-gate: always` today.
  If one is ever relaxed to `conditional`, **any plan with a `## Wording spec` section still stops at
  the human plan gate.** That's this file's rule; it doesn't depend on the engine's frozen-vs-live
  diff at step 5, which compares only `## Approach`. If the architect's review changes the
  reader-facing output, ask `ba` again before that stop.
- **Implementation applies both halves on the branch.** The orchestrator applies the label spec to
  code (`dashboard/explore/labels.py`, and wherever else *Who writes wording* says the wording lives)
  and the glossary delta to `docs/glossary.md`, so both land in the same PR. `ba` doesn't edit the
  working tree itself, which keeps the engine's rule that a writing agent's changes come back to the
  parent to apply.
- **No wording of the orchestrator's own.** A reader-facing string the spec doesn't cover goes back
  to `ba`. Wording `ba` adds after the plan gate goes in the PR body under a **Wording not yet
  approved** heading at the end of the summary, listing each key and its wording. The owner approves
  it at the merge gate, or it's fixed on the branch first; **a PR with that heading stops at the
  merge gate under every mode**, so a graduated route can't auto-merge it. **If
  the owner merges while deferring approval** (to review it on the live dashboard, or pending a
  historical-claim check), the PR marks the term's glossary entry as wording pending and adds a row
  under `## Open decisions` before it merges. Use the status form `docs/glossary.md` uses at the
  time: #354 settles it as `settled; wording pending (<what awaits the owner>)`, and until #354
  merges the file's existing `**Status:** settled.` line plus a sentence naming what awaits the
  owner. That edit is a new commit after the verdicts came in, so the engine's rules decide which
  gates it re-arms before the merge. The heading covers wording on an open PR; the glossary status covers wording that has
  merged unapproved (owner decision on #369, 2026-10-15; recorded on #354). If `ba` can't be invoked
  or returns no spec, journal `- gate-error: wording-spec — ba — <reason>` and stop for the human.
- **Every iteration records the wording step.** Otherwise "not due" and "never ran" look the same in
  the journal. Step 5's gate-decision block, beside its `- Plan-gate:` line, carries exactly one of
  these (every iteration that reaches step 5 writes that block, and under `plan-gate: always` it is
  written before any open record), and the close record repeats it:
  - `- Wording-spec: <n> keys (ba); value line (ba)`: due, and `ba` returned a spec of `<n>` keys
    and the value line.
  - `- Wording-spec: n/a: no reader-facing output; value line (ba)`: no spec due, and `ba` returned
    the value line.
  - no `- Wording-spec:` line: `ba` couldn't run or returned nothing, or the tree wasn't clean before
    the call, so `- gate-error: wording-spec — ba — <reason>` or
    `- gate-error: wording-spec — git status — tree not clean before ba` stands in for it and the
    iteration stops.

  A row resumed past the plan step writes no new line: its plan step already wrote one, and the
  close record carries that one forward. The close record adds what changed after the plan step:
  `; <m> keys added after the plan gate` when `ba` added wording later, and
  `; ba wrote <path> at the plan step, restored` when the check above found a write. An `n/a` that
  code review later proves wrong stays as written. The review finding records it, and its fix goes
  back to `ba`.
- **Code review checks two things on every diff** (`CODE_REVIEW` is always given both, whether or not
  the plan has a wording spec, so a plan that missed its reader-facing output is still caught):
  1. **Spec match.** A reader-facing string added or changed in the diff that the wording spec
     doesn't carry, or that differs from it, is a BLOCKING finding. The spec is the plan's table plus
     anything `ba` added since.
  2. **Key index.** A diff that adds, renames, changes or removes a `LABELS` key, a closed value
     (a `pv_status` or count-status label, a party display form) or a reader-facing string either
     updates `docs/glossary.md` to match, or the PR body names a filed `ba` follow-up issue. **A diff that does neither
     gets a BLOCKING finding.** The orchestrator files the follow-up (`gh issue create
     --body-file`); `ba` has no GitHub write tools. "To match" means: a `LABELS` key has its row
     in `## Key index`, which lists `LABELS` keys only; a closed value or other reader-facing
     string has a defining entry whose **Shown as** names the constant that ships it. A string
     with no glossary term at all is a finding for `ba`, not a new Key index row.

  **Not these:** `TestNoRawValues` already fails an underscore or a served code in rendered text, and
  `TestLabels` a `LABELS` key that isn't a public `/v1` field (`dashboard/CLAUDE.md`). The two checks
  are for what those tests can't see, wording that differs from the spec and drift between the code
  and the glossary, so neither re-checks what a test already guards.
- **The two checks have their own verdict.** `CODE_REVIEW` is a skill invoked by name, so the loop
  has no prompt of its own to put the checks in, and nothing shows whether the skill applied them.
  So:
  - **Round 1** also spawns a fresh **wording finder**: a `ba` agent given the round's commit range,
    the acceptance criteria, the plan's `## Wording spec` plus anything `ba` added since, and the two
    checks above. Its prompt tells it to edit no file, and the "wrote nothing" checks above apply to
    it as well. A round reads commits, so the tree is clean then too; if it isn't, the round stops as
    at the plan step, with `- gate-error: code-review — git status — tree not clean before ba`. A
    write it made is recorded on the round's `- Code-review:` line.
  - **A later round** is the engine's one lighter checker, not a second agent beside it. The
    orchestrator composes that checker's prompt, so the two checks go in it, under the same
    reporting rule.

  Whichever agent carries them must report a result for each check by name: `spec match: clean` or
  its findings, and `Key index: clean` or its findings. Its findings are BLOCKING as the checks say,
  and the engine's rules for the round they arise in decide what follows. The round's
  `- Code-review:` line records both results and names the carrier, for example
  `wording (ba): spec match clean, Key index 1 finding` in round 1, or `wording (checker): …` later.
  **A round without both results is not clean.** Spawn the carrier again once, fresh, and note the
  retry on the `- Code-review:` line. If the retry also lacks a result, journal
  `- gate-error: code-review — wording checks — <check> result absent` and escalate. A wording
  finding the skill raises counts the same as one from the finder.
- **The merge gate lists every Key-index deferral.** Each `ba` follow-up filed under check 2 during
  the iteration goes in the PR body under a **Key-index follow-ups** heading at the end of the
  summary, with its issue number and the keys it covers. **A PR with that heading stops at the merge
  gate under every mode**, and the stop names each one, so the owner approves every deferral
  explicitly. A deferral the owner doesn't approve is fixed on the
  branch before the merge, and the engine's rules decide which gates that change re-arms. With none
  filed, the stop says "Key-index follow-ups: none".

**Not here:** marketing prose (posts, announcements, the dashboard's planned narrative tabs) follows
*Who writes wording*'s `marketer` route; `ba`'s term check on a draft is not a label spec and needs no
`## Wording spec`.
