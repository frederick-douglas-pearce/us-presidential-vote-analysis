# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Analyzes historical US Presidential Election data (**1824–present, complete** — `UNSUPPORTED_EC_YEARS` is now empty. The two contested Reconstruction elections were the last holdouts: 1868 landed in #143/D044 with Georgia's contested nine votes flagged `count_status='disputed'` rather than resolved by picking one of the page's two totals rows, and 1872 in #144/D045-D046, which synthesizes the 17 cast-then-rejected votes the Archives table omits entirely, restores Arkansas's and Louisiana's allotments to reach the 366 denominator Congress announced, and adds a second electoral-vote measure so the fact can state both what electors **cast** and what Congress **counted**) to compare Electoral College vs. Popular Vote outcomes, plus a proposed hybrid (average of the two). The work is a multi-step data pipeline that scrapes, transforms, validates, and loads data into an `elections` PostgreSQL database. Step 1 originated as a Jupyter notebook and is being migrated into the installable `usvote` package (see [`src/usvote/` package](#srcusvote-package-in-progress-migration)); steps 2–3 remain planned.

- `step1_electoral_college_data.ipynb` — **implemented.** Scrapes Electoral College vote data from the [National Archives](https://www.archives.gov/electoral-college/results) and loads it into the `dwh` (data warehouse) schema.
- `step2_popular_vote_data.ipynb` — planned. Popular vote data from UC Santa Barbara, added to the same warehouse tables.
- `step3_voting_data_analysis.ipynb` — planned. Analysis, visualizations, and a data mart schema for dashboards. The three-method computation core that this step's analysis rests on is **already built** outside the notebook, in `usvote/hybrid.py` (see below).

Alongside the pipeline the repo carries a **publishing workstream** — the "Counted, Not Assumed" blog series in [`posts/`](posts/), its drafts in the git-ignored `social/`, and the scripts and CI gates that ship them. It shares no code with the pipeline; see [Publishing](#publishing-posts-social-tooling--a-second-non-pipeline-workstream).

## Environment & Running

The original step-1 analysis is notebook-driven, but the `src/usvote/` package now
has quality gates (run via `uv`, enforced in CI):

```
uv run pytest                    # unit suite (live-Postgres integration excluded)
uv run pytest -m integration     # live-DB tests (needs USVOTE_TEST_DB_*)
uv run pytest --cov=usvote       # branch coverage report
uv run ruff check                # lint: E,F,I,UP,B,SIM,C4 @ line-length 88
uv run mypy                      # type check: src + tests
```

Test layout: unit tests are offline (no network/DB); the two live-Postgres tests
carry `@pytest.mark.integration` (the marker, not the directory, is what selects
them). `tests/unit/` and `tests/integration/` are the documented homes for new
tests; `tests/fixtures/` holds saved Archives HTML replayed offline.

Two fixture caveats specific to UCSB (D014/D016/D022): the Archives fixtures are real
saved bytes, but **every `ucsb_synthetic_*.html` fixture is hand-written** — UCSB grants
no reuse rights and this repo is public, so no UCSB bytes are committed and
`test_no_fixture_ships_real_ucsb_bytes` guards that. The real 60-page snapshot is the
acceptance corpus for the UCSB parser and lives outside the tree; `TestRealCorpus` in
`tests/unit/test_ucsb_parse.py` runs against it and **skips when `USVOTE_UCSB_HTML_DIR`
is unset**, so CI stays green and never touches UCSB. Run it locally with that env var
set — it is the only check that exercises all six header layouts against real markup, and
(via `test_ucsb_transform.py`) the only one that runs the D024 two-way roster assert over
all 51 in-scope years.

One fixture runs the other way: `tests/fixtures/ec_state_roster_by_year.json` is a
committed snapshot of the **Electoral College** participation roster (public-domain
Archives data, so D022 does not apply), which lets the UCSB roster logic be tested offline
against real 1824/1864/1876 shapes. It is **test input only** — a test asserts nothing
under `src/` reads it, so it cannot become a second source of participation truth (D006) —
and it deliberately carries no electoral-vote counts (D024 §5).

```
uv sync                          # create the venv + install deps from pyproject.toml + uv.lock

python -m usvote                 # run the packaged EC pipeline (create-if-absent load)

python -m usvote all             # build the whole warehouse (EC + MIT + optional UCSB + views)
python -m usvote.snapshot        # build the read-only API SQLite snapshot (E8; needs the warehouse)

```

The API also ships as a **cloud-agnostic container** (E8-S6, #100 / D032). Build the snapshot first, copy it into the build context, then `docker build` + `docker run` (the running image needs no DB — the snapshot is baked in, so snapshot-version == image-version):

```
python -m usvote.snapshot                    # build the snapshot (needs the warehouse)
cp "$USVOTE_API_SNAPSHOT_PATH" ./api_snapshot.sqlite   # into the build context (git-ignored)
docker build -t usvote-api .                 # slim (~150MB): serve-only deps, snapshot baked in
docker run --rm -p 8080:8080 usvote-api      # listens on $PORT (default 8080); curl /health
```

The image is **slim by design** ([D033](.claude/specs/decisions.md)): `usvote/api/` imports only FastAPI + stdlib (the D028 import-graph invariant), so the container installs the package `--no-deps` plus the lock-pinned `serve` dependency-group — the heavy stack (pandas/geopandas/psycopg2/matplotlib) stays out. Serve versions come from `uv.lock`, never hand-pinned in the `Dockerfile`. A CI `docker-build` job builds + boots the image against a synthetic placeholder snapshot (`scripts/make_placeholder_snapshot.py`) — the drift guard that catches an allowed-but-unpackaged import the denylist import-graph test would miss.

**Public deployment (E8-S7, #101 / D034).** The container is deployed to **Cloud Run** (scale-to-zero, `--max-instances=1`, request-based CPU) fronted by **Cloudflare (free)** for CDN + rate limiting + bot protection. Runbook: [`docs/deploy-cloud-run.md`](docs/deploy-cloud-run.md); deploy glue: [`.github/workflows/deploy.yml`](.github/workflows/deploy.yml) (keyless WIF, `workflow_dispatch`-only). The snapshot is a **data input** built locally from the warehouse → uploaded to a private GCS bucket → pulled into a CI-built, snapshot-hash-tagged image (never built in CI — no warehouse there). **Caching is version-based, not TTL** (D034): the response header stays moderate (`public, max-age=3600, stale-while-revalidate=86400, stale-if-error=86400`), the *long* hold lives in a Cloudflare Edge Cache TTL, and the deploy **purges the edge after cutover** — so between snapshot versions the origin is never woken by reads (true scale-to-zero). **Origin lock-down** (`usvote/api/origin_guard.py`): a stdlib-only middleware rejects direct-to-`run.app` `/v1` hits lacking a Cloudflare-injected secret header — **opt-in + fail-open** (active only when `USVOTE_API_ORIGIN_SECRET` is set; `/health` always exempt; posture surfaced in `/health`), so local dev, the unit suite, and the D033 container smoke test are unaffected. A **budget kill-switch** ([`deploy/killswitch/`](deploy/killswitch/)) pauses the service if spend crosses a threshold (Cloud Run has no native hard cap). The Cloudflare front is a **Worker** (`usvote-api-proxy`), not zone Rules — the free plan paywalls Origin Rules' Host-header override, so the Worker rewrites `Host`→`run.app` (Cloud Run's front end routes by Host — a plain proxied CNAME 404s), injects the secret header, and caches `/v1` via the Cache API ([D035](.claude/specs/decisions.md), revising D034's mechanism; intent unchanged). **Live at `https://api.us-presidential-election-center.org`.**

Python >=3.11 (developed on 3.14). Dependencies are pinned in `pyproject.toml` + `uv.lock` (`beautifulsoup4`, `requests`, `pandas`, `geopandas`, `matplotlib`, `psycopg2`, plus the dev/notebook tools).

Prerequisites before running step 1 (both the package and the notebook read these from the environment — see the README "Configuration" section; externalized in #31):
- **PostgreSQL** (>12.9) with a database named `elections` and create-schema/table permissions. Connection params come from the standard libpq `PG*` env vars (`PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`); `PGPASSWORD` is prompted at runtime via `getpass` when unset.
- **US States shapefile** (TIGER2019 from census.gov), located via the `USVOTE_SHAPEFILE_PATH` env var. `geopandas` reads state geography (region, area, lat/lon) from it.
- Internet access for scraping — **unless a local Archives corpus is present** (#89). `python -m usvote corpus` fetches every in-scope year page plus the results index into `USVOTE_EC_HTML_DIR` (stored outside the repo, alongside `ucsb_raw/`, and mirroring that corpus's layout: `<year>.html` + `_index_results.html` + a `manifest.json` carrying per-page sha256/bytes/status/timestamp/url). When the variable is set, `python -m usvote [ec|all]` **auto-detects the corpus and rebuilds with zero network requests** — the path that feeds the API snapshot (D034), which otherwise re-scraped ~50 pages on every warehouse refresh. The corpus is verified complete before use (`assert_corpus_covers_years`): a stale corpus missing a year fails loud rather than silently building a warehouse short that year. `--no-corpus` forces the live scrape. The snapshot honors archives.gov's `Crawl-delay: 10` and sends a truthful User-Agent, so a first run takes ~8.5 min; the live scrape path does **not** yet do either (tracked separately).

Both `python -m usvote --replace` and running the notebook top-to-bottom scrape all election years, build the three DataFrames, and **drop and recreate** the `dwh` schema (`create_tables_from_dfs(..., replace=True)` cascades a schema drop). Be deliberate about executing the write path.

## Architecture

### Pipeline shape (step 1 notebook)

The notebook follows a strict Scrape → Transform/Validate → Load structure that mirrors its section numbering:

1. **Section 2 — Scrape.** `scrape_election_links` → `scrape_raw_election_tables` → `parse_election_years` walk the Archives site. Each election year page has two HTML tables: **Table 1** (top-2 candidates + party) and **Table 2** (candidate home states + a votes-by-state matrix). Parsing produces `parsed_election_years`, a list of per-year dicts with keys `t1`, `t2.candidate_state`, `t2.votes_by_state`.
2. **Section 3 — Transform & validate.** `pd.json_normalize` flattens the parsed structure into three DataFrames, each transformed and validated independently before a final join:
   - `candidates_df` (Candidate dimension) — built from Table 2 states + Table 1 parties, joined on candidate name.
   - `state_df` (State dimension) — US state names joined to the geopandas shapefile data.
   - `votes_df` (Votes fact) — the melted votes-by-state matrix, joined to both dimensions to attach `candidate_id` and `state`.
3. **Section 4 — Load.** `DBC` (from `db_tools.py`) writes all three DataFrames into the `dwh` schema.

The E2 refactor is complete: every module below is ported and runnable (the `python -m usvote` entry point wires scrape → parse → transform → load). The notebook is **retained** while the migration proceeds — the "keep the notebook vs. fully migrate off it" decision (D003) is still open. The layout mirrors the notebook's own section numbering:

**Source-namespacing convention.** The top-level `usvote/` modules are the **Electoral College / National Archives** pipeline — the source-of-truth spine (D006). The two popular-vote sources land as sibling subpackages, `usvote/ucsb/` (E4) and `usvote/mit/` (E5), each with its own scrape/parse/transform/load and a `pipeline.py` wiring the stages (`run_mit_pipeline`, `run_ucsb_pipeline`). EC stays flat by design; PV sources nest.

**Entry points (unified in #84b, subcommand-based).** Every package `__main__` now dispatches subcommands, and the collision the issue named ("same spelling, different meaning") is **reduced to a documented default, not eliminated**:
- `python -m usvote` — bare stays **EC** (backward-compatible; `--replace` still works bare). Subcommands: `ec` (the explicit bare default) and `all` (the whole-warehouse build — EC + MIT + optional UCSB + join views, via `usvote/warehouse.py`).
- `python -m usvote.ucsb` — bare stays **snapshot** (the D023 network refresh into `USVOTE_UCSB_HTML_DIR`). Subcommands: `snapshot` (default) and `load` (run `run_ucsb_pipeline`).
- `python -m usvote.mit` — new symmetric `__main__`; single `load` subcommand (default). MIT reads a local CSV, so there is **no** `snapshot` — the source asymmetry is preserved, on purpose.

So `python -m usvote` loads and `python -m usvote.ucsb` snapshots: the bare spellings still differ across packages (principled — only UCSB has a network stage to snapshot), but each is now a *named default subcommand* rather than an undocumented surprise (D027). `python -m usvote all` is the unified "load everything" front door. Per-source `python -m usvote.mit load` / `python -m usvote.ucsb load` remain the way to load a single PV source (`usvote all` is the only cross-source orchestrator, so there is no top-level `mit`/`ucsb` subcommand — one spelling per action). Both PV `load`s require the EC spine already loaded (they reconcile against `dwh`); run `python -m usvote` (or `all`) first.

`usvote/warehouse.py` is a **composition root** (E6-S3, #84b) — a fifth kind of top-level module, distinct from the `spine.py`/`years.py`/`join.py` EC-domain family. It sequences EC → MIT → (optional) UCSB → view rebuild → the #167 overlap gates (`run_warehouse`; `rebuild_views` is the one place the `pv union → join → hybrid` ordering is expressed), and it is the one top-level module that imports *from* every source (EC + both PV subpackages). That does not violate the D015 source-to-source prohibition: a composition root sits **above** both EC and PV, exactly like `__main__`, so it is exempt (D027). The invariant that keeps the exemption honest runs the other way — **nothing under `usvote/{mit,ucsb,pv}/` may import `usvote.warehouse`** (a back-import would invert D015 into a cycle), enforced by a test mirroring the greppable `dwh.votes` guard. The warehouse build is **per-source atomic, not globally atomic** (each pipeline owns its own transaction, #84a; the orchestrator opens none): a mid-build failure leaves the committed sources in place, and the honest recovery is `run_warehouse(..., replace=True)` — *not* a bare re-run, which would hit a unique-violation on the first already-loaded source. **That recovery does not apply to a D017 layer-3 breach** (#167): those gates are the *last* step, deliberately, so the warehouse and every view are already built when one fires — `replace=True` rebuilds the same facts and re-hits the same breach. The escape is `--no-validate-overlap` (or `validate_overlap=False`), which exists because gate 1's per-year floor is the threshold D051 says to expect to retune first. Because `run_ec_pipeline(replace=True)` does `DROP SCHEMA dwh CASCADE` (taking the PV tables and views with it), the join views are **always rebuilt** as the final step — `run_warehouse` is what E7/E8 rely on to leave `ec_pv_preferred`/`ec_pv_redistributable` — and, since #124, the four `hybrid_*` views — populated after a `--replace` build.

Two shared, **source-neutral** things sit between them — the `usvote/pv/` package and the `usvote/years.py` module — and the dependency always runs `source -> shared`, never source-to-source. `usvote/pv/` holds the contracts both PV sources conform to — `schema.py` (the D018 record shape + `dwh.pv_votes` DDL), `status.py` (the D024 `pv_state_status` roster shape, the `pv_status` enum, and the two-way roster/fact assert), `validate.py` (the frame invariants both sources assert — `assert_pv_grain` and `assert_totals_not_exceeded`, #82; kept out of `schema.py` because they constrain data *values*, not the D018 column/DDL contract), `views.py` (the three D017 resolution views over the raw union), and `load.py` (the two write seams, `load_pv_records` for the fact and `load_pv_status` for the roster).

`usvote/pv/overlap.py` (#167 / D051) is the **D017 layer-3 gate** — the tolerance D017 §3 declared and never shipped, calibrated by #70 and adopted as D051. It sits on `validate.py`'s shelf (invariants over data *values*) and belongs under `usvote/pv/` for the same reason the roster contract does: it compares two sources, so neither source's subpackage can own it (D015). Two of D051's three thresholds live here — gate 1's exact-match-rate floor (≥90% overall, ≥80% any year) and gate 2's per-cell relative ceiling (flag at 1% → the D005 list, fail at 15%), both at the `(year, state, candidate)` cell grain over `pv_redistributable` vs `pv_ucsb`, **never** the raw union. **Gate 3's placement is forced, not preferred**: the national margin-difference ceiling (≤0.25 pp) derives its margin with `roll_up_national`, so a home here would need the `pv -> hybrid` import `test_layering.py` forbids — it lives in `hybrid.py` beside the computation it protects. The relative-delta basis is `|MIT − UCSB| ÷ **UCSB**`, asymmetric and therefore part of the decision rather than an implementation detail. **No magnitude leaves the module**: `OverlapKey` carries `(year, state, candidate)` plus party for display and has no numeric field, which makes D030/D022 structural rather than a matter of discipline — MIT is CC0 and exactly reproducible, so an attributed *relative* delta inverts to the UCSB integer. **A year only one source reaches is excluded only at or beyond the spine frontier** — `max(ec_ingest_years())`, the newest election the EC spine knows about (`pv -> years`, the direction `pv/absences.py` already takes). At the frontier, one source publishing first is ordinary asymmetric refresh (MIT is a CSV drop, the UCSB corpus a manual snapshot), and the bound is inclusive because the frontier year is precisely the one legitimately one-sided mid-cycle. **Below** it, a one-sided year is a regression: it stays in the population, reads 0%, and trips gate 1's per-year floor. **The frontier is the spine's, not the data's, and that is the point** — an earlier form took it from the frames themselves (`min(max MIT year, max UCSB year)`) and was *circular*, letting the data define the boundary meant to detect the data being wrong: a MIT CSV truncated at 1996 pulled the ceiling down with it, excluded seven elections and reported **100% agreement** on the remainder while 2000–2024 vanished into the snapshot and the public API. Deriving it from `ec_ingest_years()` rather than `LATEST_ELECTION_YEAR` means a year gated back into `UNSUPPORTED_EC_YEARS` moves the frontier down with it, and adds no new thing to maintain — the cycle bump the spine already needs moves this too. Gates 1–2 are the **only** instrument pointed at a *MIT* coverage hole, since MIT's D024 roster derives its in-scope years from the rows MIT actually loaded; **UCSB is not symmetric** — it derives scope from the spine and `_scope_years` raises on a missing page before the warehouse is built. The stated limit is a source dropping the **frontier year itself** — MIT losing 2024 is excluded by the very clause that lets a mid-refresh 2024 through, so it reads 100% green; only the frontier is exposed that way, since nothing below it is ever excluded. Its owner is a MIT year-contiguity guard (#177) rather than a second clause here. Both gates **skip, never fail**, when UCSB is absent, so a public EC + MIT clone is unaffected — which also means the gate cannot run in CI (D022) and its acceptance evidence is local-only.

`usvote/pv/absences.py` (E8-S9 prereq, #140) is the one module under `usvote/pv/` that carries **data and a derivation** rather than a contract, and it belongs there for the same reason the roster contract does: which states held no popular vote is a fact about the *election*, source-neutral. It holds `PV_ABSENCE_CATALOG` — the **32 pre-1976 `(year, state)` absences** (18 `legislature_chosen` + 14 `not_participating`), each a `PVAbsence(pv_status, citation)` carrying a **public-domain** citation (*McPherson v. Blacker*, 146 U.S. 1 (1892) for the 1824/1828-1860 legislative appointments; Colo. Const. of 1876 Schedule § 19 for Colorado; the H.R. 126 joint resolution for 1864). It exists because the pre-1976 classifications previously had exactly one origin — parsing UCSB's markup — and UCSB grants no reuse rights (D022) while the snapshot is redistributable-only *at the source* (D030), so a public `pv_status` back to 1824 (#139) cannot be built on UCSB-derived rows. The **derivation is single-sourced in `status.py`**: `build_roster(..., absences=...)` takes the map and `popular_vote` is the **residual**; `build_popular_vote_roster` is the empty-map call (MIT) and `build_curated_roster` is the catalog-bound one, so the dependency runs `absences -> status` and `status.py` still imports nothing from `usvote`. Two properties are enforced rather than conventional: `CURATED_YEARS = frozenset(ec_ingest_years())` (with a count pin) makes scope explicit so the catalog's *silence* about an unreviewed year cannot read as "no absences" — `build_curated_roster` **raises** outside it. That pin is what made #143 (ingesting 1868) a deliberate act: the four 1868 rows were curated here in #140 while the year was still gated, so admitting them needed **no new research**, only lifting `UNSUPPORTED_EC_YEARS` and bumping `CURATED_YEAR_COUNT` 49 → 50 (and again 50 → 51 in #144, where 1872 was reviewed and found to have **no** absences — a finding, not a silence, though the corroboration is the UCSB cross-source control test rather than the spine: with AR/LA's allotments restored the year has no zero-EV state, so the spine check inspects nothing there, and it is blind to `legislature_chosen` absences in any case since those states appointed electors); and `assert_catalog_matches_spine` cross-checks against the EC spine in **both** directions, the second (no zero-EV spine state may be left `popular_vote`) being the one with teeth, since the residual would otherwise absorb a newly-zero-EV state silently. `tests/unit/test_layering.py` proves the firewall structurally in both directions — the catalog imports/reads nothing UCSB (proved in a subprocess with `usvote.ucsb` made unimportable, not grepped), and nothing under `usvote/ucsb/` imports the catalog, which is what keeps `TestRealCorpus`'s cross-source control test non-circular: **UCSB validates the catalog, never feeds it**. That control test agrees on the **classification** of all 2,204 `(year, state)` pairs across 51 years — note that the shared *membership* is the design, not a finding, since D024 §6 has both sources derive it from the same EC spine, so what it independently corroborates is the `pv_status`, above all the 32 absences — and it **skips in CI** (D022), so running it with `USVOTE_UCSB_HTML_DIR` set is a merge precondition; the 14 `not_participating` rows are the CI-provable subset, verified both ways against the committed zero-EV fixture. Catalogued in [`docs/corrections.md`](docs/corrections.md), whose third section states plainly that it is **not a correction to anybody's data**.

`usvote/years.py` holds the election-year domain constants (`ec_ingest_years`, `UNSUPPORTED_EC_YEARS`) and is deliberately dependency-free, so a pure transform can derive its year scope from the EC spine without importing the orchestrator (and its DB/network stack). `usvote/pipeline.py` re-exports those names.

`usvote/count_status.py` (#143 / D043 §3, D044; extended in #144 / D046) is the second member of that dependency-free family and exists for the same reason: the `dwh.votes` count-status enum (`counted` / `not_counted` / `disputed`, plus `build_count_status_check`) has **two callers that must not depend on each other** — `transform.py` *assigns* the values, `load.py` builds the `CHECK` from them. Parking the tuple in `transform` would point the DDL builder at the pandas transform module; parking it in `load` would drag psycopg2 into the transform import chain. Stdlib-only, exactly as `usvote/pv/status.py` is for `pv_status`, and the CHECK-built-from-a-value-tuple pattern is lifted from it (D024 §4). The status answers "were these cast votes actually **counted** by Congress?" at the `(year, state, candidate)` grain (D043 §4 — 1872 Georgia counts 8 of its 11 and rejects 3, so a `(year, state)` roster cannot express it), and is deliberately disjoint from `ELECTORAL_VOTE_SHORTFALLS`, which records votes **never cast**; the disjointness is structural, since a cast-then-rejected row still sums to its allotment. #144 added the module's second export, `COUNTED_VOTES_COLUMN` (+ `build_counted_votes_check`), for the same two-callers-that-must-not-depend-on-each-other reason — and it belongs here rather than in `transform.py` because **the enum is its definition**: a row's counted votes are its cast votes when `counted`, else 0.

`usvote/spine.py` is a fourth kind of thing: **EC-spine readers** (`read_ec_participation`, `read_ec_getters`) that a PV source uses to pull EC facts back out of `dwh.votes`/`dwh.candidate` across a DI seam. It lives at the top level (not under `usvote/pv/`) because it embeds EC-star-schema knowledge — nothing under `usvote/pv/` names `dwh.votes`. Its precedent is `usvote/years.py`: an EC-domain module a PV stage reads *from*.

`usvote/join.py` is the **EC<->PV join seam** (E6-S2, #69 / D026) — another top-level EC-domain module in the `spine.py`/`years.py` family (it names `dwh.votes`/`dwh.candidate`, so the same greppable invariant keeps it out of `usvote/pv/`). It joins a **resolved** PV series onto the EC spine — `pv_preferred` (analysis/E7) or `pv_redistributable` (API/E8), never the raw `dwh.pv_votes` union (D017, else the 1976–2024 overlap fans out 2×) — as an **EC-left join** at the canonical `(year, state, candidate)` grain, exposed as `ec_pv_preferred`/`ec_pv_redistributable`. EC-left is correct because the EC `votes` fact is **dense**: the Archives prints `-` for "no electoral votes here", which the parser reads as `0` (`parse.py`), so a *loser is an explicit 0-EV row, not a missing one* (verified rectangular across all 51 years; ~59% of rows are such 0-rows, now guarded by `transform.assert_rectangular_state_grain`). So the loser rows the thesis needs — "lost the EC, won the PV" — survive the LEFT JOIN with their real EC votes and PV attached; a getter with no PV keeps NULL PV (an honest D005 gap). `national_electoral_votes` is a `SUM(...) OVER (PARTITION BY year, candidate_id)` window (exact on the dense fact), joined since #144 by `national_counted_electoral_votes` (the same window over the counted measure) and the per-row `president_electoral_votes_counted` that coverage policy (c) re-sums over a restricted state set (D046) — both **appended** to `EC_PV_COLUMNS`, never inserted, because `CREATE OR REPLACE VIEW` can only add trailing columns and a mid-list insert breaks `rebuild_views` against any existing warehouse. #139 appended two more for the same reason — `count_status` + `count_status_reason`, the row-grain fact D043 §4 fixes (the view excludes `is_total` rows, the one place D044 says the status must not be read) — and **surfaced all four publicly** (D047/D048). Note the containment property that made that a *deliberate* step rather than an automatic one, and which still holds: `snapshot_schema.DATA_COLUMNS` is an **independent explicit projection**, not derived from this tuple, so adding a column here reaches neither the snapshot nor the content hash until someone lists it there too. The direction is one-way by design (D047 §3) — a test asserts `DATA_COLUMNS ⊆ EC_PV_COLUMNS ∪ derived`, and the reverse assert is forbidden. The one EC-left footgun — a PV row matching no EC row is silently dropped — is caught by a **fact-level anti-join** (`assert_db_pv_matches_ec`) run as a view-creation precondition (the reciprocal guard `docs/canonical-keys.md` describes). (An earlier draft used a FULL OUTER "participant" view on the false premise that the fact was *sparse*; the corrected D026 records why EC-left replaced it.)

`usvote/hybrid.py` is the **three-method computation core** (E7-S2, #121 / D037/D038/D041) — another top-level EC-domain module in the same family (it names `ec_pv_preferred` and `dwh.pv_state_status`, so the same greppable invariant keeps it out of `usvote/pv/`; that invariant is now **enforced** by `tests/unit/test_layering.py`, which also forbids any `usvote/{mit,ucsb,pv}/` module importing it). It rolls a **resolved** join view up to per-`(year, candidate)` national outcomes and derives the three method scores: the EC share, the PV share, and the **hybrid** — `(ec_share_hybrid + pv_share) / 2`, the average of the two ratios, highest average wins (D037). Two grains: `build_hybrid_frame` (per candidate) and `build_hybrid_summary` (per election — the three winners, `ec_determinative` and `pv_coverage`, plus, as of #123/E7-S4, the two flips and the three margins). `HYBRID_SUMMARY_COLUMNS` is therefore **twelve** columns, and #123 **appended** its five rather than inserting them — the same `CREATE OR REPLACE VIEW` constraint that governs `EC_PV_COLUMNS` (D047) binds here too as of #124, which materialized the tuple as the `hybrid_summary_preferred` / `hybrid_summary_redistributable` views. The order is held by a **hand-written literal** assert (`TestShape.test_the_summary_column_order_is_pinned_to_a_literal`, the twin of `test_join.py`'s `EC_PV_COLUMNS[:15]` pin), and it has to be a literal: the summary frame is built with `columns=list(HYBRID_SUMMARY_COLUMNS)`, so any assert comparing the frame against the constant is circular and passes under a reorder or a mid-list insert alike — as #123's review proved by monkeypatching it. `HYBRID_CANDIDATE_COLUMNS` gained the equivalent literal pin in #124, where the tuple became a view column contract; both tuples are now append-only, and with `hybrid_summary_*` sitting on top of `hybrid_*` a breaking change needs a `DROP ... CASCADE` migration rather than a `CREATE OR REPLACE`. `pv_flip` / `hybrid_flip` compare each method's winner against the EC baseline (`argmax(ec_share_full)`, the rank-1 leader — **never** `took_office`, which diverges in a contingent election) and are **nullable**: a method with no winner yields NULL, never `false` and — the trap the guard exists for — never `true`, since `_winner` returns a Python `None` rather than `pd.NA` and a bare `!=` would report a flip on every **pre-1976** year when UCSB is absent — MIT still covers 1976–2024, so 13 of the 51 years are unaffected. `ec_margin` / `pv_margin` / `hybrid_margin` are top-2 **percentage-point** gaps (D037) taken over **each method's own non-NULL scores** — necessary, not fastidious, because 4 of the 13 redistributable years carry a candidate with electoral votes and no popular vote (faithless electors; five of 2016's seven rows), so the three top-2 sets genuinely differ within one year. With fewer than two scored candidates a margin is NULL, never `top1 - 0`. `ec_margin` reads the policy-invariant `ec_share_full` so it stays coherent with the `ec_winner` and `ec_determinative` derived from that same column, while `hybrid_margin` tracks `hybrid_score`; the asymmetry is deliberate.

The **EC share is deliberately split in two**, and the split is a safety property (D037/A): `ec_share_full = national_counted_electoral_votes / ec_denominator` is policy-invariant and the **only** input to `ec_determinative`, while the policy-selected `ec_share_hybrid` feeds `hybrid_score` alone. So no coverage policy can manufacture a constitutional majority that never existed. The failure it guards against is the **naive** restriction — trimming 1824's denominator to the popular-vote states while leaving the numerator alone — which reads Jackson at 99/190 = 0.52, over the line, when the real answer is 99/261 = 0.379 and the House decided the election. Policy (c) as implemented does **not** make that mistake (it restricts both halves, giving 84/190 = 0.442), but the split is what makes the mistake unable to matter even if a future policy commits it. `ec_denominator` is the **appointed** allotment (each state's `total_electoral_votes` counted once — a bare aggregate over the joined rows would multiply it by the candidate count), exactly the 12th Amendment's "majority of the whole number of Electors **appointed**", while the numerators are votes **counted** (#144 / D046 — they were votes *cast* until 1872 forced the distinction; both gaps in the appointed ≥ cast ≥ counted ladder are documented, and the switch is strictly safer since a smaller numerator can only shrink a share). Both gaps therefore make candidate EC shares sum to **≤ 1.0, never == 1.0** — 2000 is Bush **271 of 538 appointed** against a **270** threshold, not against the **269** a cast basis (537 ÷ 2, rounded up) would have set — the contrast is between the two *thresholds*, not two tallies of Bush's votes, which are 271 either way (D041); 1872 is Grant **286 of 366 appointed** against the **184** Congress announced, not 286 of the 352 the Archives page itself totals. `president_electoral_rank` moves to the counted basis with it, and the co-switch is mandatory rather than incidental: `assert_ec_winner_matches_rank` compares `argmax(ec_share_full)` against rank 1, so a half-switch would fire it on 1872 alone. No winner and no `ec_determinative` outcome changes across the 51 years — in both anomaly years the EC winner is Grant, whose votes were entirely counted — but 1868 Seymour's `ec_share_full` moves 80/294 → 71/294. `ec_determinative` is `true` only on a **strict** `> 0.5`; `false` means *no EC majority*, a populated and expected state — the hybrid's motivating case — never a null-because-broken.

The **`dwh.pv_state_status` roster is a first-class input**, not a later bolt-on: `EC_PV_COLUMNS` carries `total_electoral_votes` but not `pv_status`, so which states are `legislature_chosen` lives only on the roster, and `pv_coverage` (Σ EV over `popular_vote` states ÷ `ec_denominator` — EV-weighted, D024 §8) **cannot be inferred from a NULL `candidate_votes`**: that would conflate a state where no popular vote ever existed with one the source merely does not cover, the exact distinction D024's no-`unknown` design preserves. The denominator policy is settled at **(b)** (D038) inside `apply_coverage_policy`; #122 adds the `policy` argument and the unshipped (c) branch. The browsable companion is [`docs/pv-coverage.md`](docs/pv-coverage.md) (E7-S6, #125) — what the column measures, why EV-weighted rather than state-count, the **twelve** verified `legislature_chosen` years (1824–1876, both weightings), the 1824 worked example (margin 8.09 → 14.69 pp under (c), winner invariant), and the surface-dependence a display consumer trips over first: those twelve values are the `ec_pv_preferred` numbers, and on the MIT-only redistributable surface every pre-1976 year reads NULL. The module **shipped no SQL until #124** (E7-S5 / D050), which materializes it as four views — `hybrid_preferred`/`hybrid_redistributable` at the per-candidate grain and `hybrid_summary_preferred`/`hybrid_summary_redistributable` per election — from one parameterized builder pair, created by `create_hybrid_views` and rebuilt by `warehouse.rebuild_views` after `create_ec_pv_views`. The translation was mechanical because the module was written for it: a view cannot `raise`, so the tie check is a **separate** `assert_no_winner_tie` that becomes a view-creation precondition, and the winner becomes a `row_number() ... DESC NULLS LAST` window. **The SQL implements policy (b) only** — (c) stays Python-reachable, which is what makes the public surface's treatment fixed rather than configurable. The pandas builders are now the **tested oracle** (the `join.py`/`pv/views.py` dual-expression pattern), and the honest limit is worth knowing: `create_hybrid_views` runs the existing guards over the *pandas* side, so a SQL/oracle drift passes all of them — only `tests/integration/test_hybrid_views.py::test_the_live_views_match_the_pandas_oracle` covers it, which is why that test is deliberately **not** corpus-gated while its AC-6 sibling is. One live-corpus finding is baked in: `party` is **resolved by `min`, not required constant**, because MIT (`REPUBLICAN`) and UCSB (`Republican`) spell one party two ways and `pv_preferred` resolves the overlap per key, not per year (D017) — `roll_up_national` is untouched, so the snapshot's rollup and content hash are unaffected. `usvote/snapshot.py`'s `build_national_rollup` **calls** this module's `roll_up_national`, so the national-aggregation derivation is single-sourced (D037/F) — one derivation, two roll-up tables (D029).

`usvote/snapshot.py` is the **API serving-store build** (E8-S1, #94 / D028) — another top-level EC-domain module in the `spine.py`/`years.py`/`join.py`/`warehouse.py` family (it names `ec_pv_redistributable`, so the same greppable invariant keeps it out of `usvote/pv/`). It materializes the `ec_pv_redistributable` join view into a **read-only SQLite snapshot** (`python -m usvote.snapshot`, writing `USVOTE_API_SNAPSHOT_PATH`) that the `usvote/api/` subpackage serves with **no live DB at serve time** — Postgres stays the local source of truth and is read only at build time (D028). The snapshot drops the internal `candidate_id` for a deterministic public `candidate_slug` (`usvote/slug.py`, D006 / `docs/canonical-keys.md`), is versioned by a content hash (not a timestamp), and is guaranteed redistributable-only at the source (D030). The serving contract (its three tables — `ec_pv`, `national_rollup`, `snapshot_meta`) is documented in [`docs/api-snapshot.md`](docs/api-snapshot.md). `usvote/snapshot_schema.py` holds just the *contract* — table/column names, `SnapshotMeta`, the schema version — and is deliberately **stdlib-only** (no pandas/DB) so both the build side and the serving side can import it across the D028 boundary.

**The served window is the full EC span, 1824–2024** (#139 / D048; it was the MIT-only 1976–2024 until then — the rows were always in the EC-left view, and `build_snapshot` filtered them away). Two windows now live in `snapshot_meta` — `year_min`/`year_max` served, `pv_year_min`/`pv_year_max` popular vote — because coverage must be *stated*, not inferred from a field of nulls. The widening is one deleted filter; almost all of #139 is the honesty scaffolding around it. Every fact row carries a **`pv_status`** (`NOT NULL`) so a null popular vote is never bare — 1860 South Carolina (`legislature_chosen`) and 1860 New York (`popular_vote`) both read null, and the two nulls mean different things. Critically, that status is derived **in-process from `usvote/pv/absences.py` over the EC spine and never from `dwh.pv_state_status`**, whose pre-1976 rows are UCSB-derived (D022) — so no UCSB-provenanced value is on the public path and D030 stays structural rather than becoming an authorized crossing; `tests/unit/test_layering.py` proves it by importing `usvote.snapshot` in a subprocess where `usvote.ucsb` is unimportable. Because the roster derives over the whole `ec_ingest_years()` span and raises on a short warehouse, **a scoped warehouse can no longer build a snapshot** — a deliberate trade that retired `SnapshotMeta`'s old scoped-subset promise. D047's plumbing lands here too: `count_status` + both counted measures are surfaced (else the API would report Grant at 300 in 1872 with no way to see 14 votes were refused), `national_rollup` gains the **appointed denominator** so a counted total is checkable at all (286 *of 366*), and provenance became **heterogeneous** — `ec_source`/`ec_license` (NARA / US-PD) beside the MIT/CC0 pair, since most of the widened table is Archives data and a `meta` block naming only MIT would claim MIT covers 1824. `count_status_reason` is the one free-text column that ships, and only because it is Archives prose from a **closed three-sentence vocabulary** the build pins it to — the same guard shape as the `pv_status` enum. `SNAPSHOT_SCHEMA_VERSION` is **2**, so a snapshot and the image serving it must cut over together (D034).

`usvote/api/` is the **serving layer** (E8-S2, #96 / D028/D031) — a FastAPI subpackage (D015), *not* an EC-domain top-level module: it sits **downstream** of the snapshot artifact and imports **only** the snapshot file + a thin `SnapshotRepository` + the stdlib-only `snapshot_schema`/`config`. It must never import `usvote.db`, psycopg2, `usvote.snapshot` (the build module, which drags pandas + the DB stack), or pandas — the D028 "no live DB at serve time" property made **structural**, enforced by `tests/unit/test_api_import_graph.py` (mirroring the greppable `dwh.votes` / `usvote.warehouse` guards). Layout: `app.py` (the `create_app()` factory + `/health` + the `/v1` router), `config.py` (`ApiSettings` — snapshot path via `config.snapshot_path_from_env(must_exist=True)`, CORS allow-list, `/v1` prefix), `repository.py` (the read-only+immutable SQLite seam; caches `snapshot_meta`, validates `schema_version` at open, fails loud at startup, and — E8-S3 — the capped by-year/state/candidate read methods), `cache.py` (the content-hash ETag + `Cache-Control` + conditional-304 machinery, pure-tested), `models.py` + `routes.py` (E8-S3), and `__main__.py` (`python -m usvote.api serve`). Serve it with `python -m usvote.api` or `uvicorn --factory usvote.api:create_app`.

The **E8-S3 read endpoints** (#97; widened to 1824 in #139) live in `routes.py` on their own `/v1` router and read *only* through `SnapshotRepository` (no SQL/parsing/aggregation/computation in handlers — the roll-up and slug are precomputed in the snapshot): `GET /v1/elections` (list covered years), `/v1/elections/{year}` (per-state rows + a sibling national `summary`), `/v1/elections/{year}/summary` (the precomputed `national_rollup`), `/v1/states/{usps}`, and `/v1/candidates/{slug}` (the public slug, never `candidate_id` — D006). Every response is a typed Pydantic model in the shared `{data, meta}` envelope where `meta.count == len(data)`; snapshot columns are renamed to public field names via `validation_alias` (`president_electoral_votes` → `electoral_votes`, `candidate_votes` → `popular_votes`, …), guarded against drift by a model↔column completeness test. Filters: `state`/`candidate` on the year endpoint, `year_from`/`year_to` on the multi-year ones (bad/inverted params → 422). A missing path identifier → typed **404**; an empty *filter* on a known resource → **200** empty. Since #139 a **pre-1976 year is no longer a 404** — it returns 200 with its EC facts, null popular votes and a `pv_status` per row; only a year that was never an election in scope (1800, 1837) 404s, and the message names the served window and the popular-vote sub-window separately. `/v1/elections` carries `has_popular_vote` per year so "which years can I compare PV for" needs no second call. The data routes call `cache_dependency` **manually after** the existence check (not as a blanket router dependency) so an unknown resource returns 404, never a 304. A server-side `MAX_ROWS` cap fails loud rather than silently truncating. OpenAPI/Swagger polish is **E8-S4**.

Because D006 makes EC authoritative, a PV source importing domain facts *from* the spine is expected (UCSB derives its year scope from `usvote/years.py`, and its state roster + candidate reconciliation from `usvote/spine.py`); what must never happen is the reverse.

### Data model (`dwh` schema)

Loose star schema: two dimension tables + one fact table. Column definitions and FK relations live in the notebook's Section 4.1 `table_column_defs`. Tables must be created in FK-dependency order (`state`, then `candidate`, then `votes`).

- **`state`** — PK `state` (full name); USPS code, census region/division, geoid, land/water area, lat/lon.
- **`candidate`** — PK `candidate_id`; parsed name parts, up to two home states (FK → `state`), up to two parties. A candidate spanning multiple states/parties is aggregated to one row with `_2` columns (e.g., Bryan D/P, T. Roosevelt R→P).
- **`votes`** — PK `votes_id`; `year`, `state` (FK, null for totals rows), `is_total` flag, `candidate_id` (FK), `total_electoral_votes`, `president_electoral_votes`, `president_electoral_rank`, `took_office` (the candidate who assumed the presidency — the EC winner (`president_electoral_rank == 1`) except in contingent elections like 1824, where the House chose someone other than the EC leader; see `CONTINGENT_OFFICE_HOLDERS` and `docs/corrections.md`), `count_status` + `count_status_reason` (D043 §3 / D044 — were these cast votes actually **counted**? `counted` / `not_counted` / `disputed`, with the source's own sentence as the reason. The enum has one definition, in the stdlib-only `usvote/count_status.py`, which `transform.py` assigns from and `load.py` builds the `CHECK` from. Deliberately disjoint from `ELECTORAL_VOTE_SHORTFALLS`, which records votes **never cast**; aggregate `is_total` rows are never flagged), and `president_electoral_votes_counted` (#144 / D046 — the **counted** twin of `president_electoral_votes`, which means **cast**. Three measures form a ladder, **appointed ≥ cast ≥ counted**: `total_electoral_votes` is the appointed allotment, `ELECTORAL_VOTE_SHORTFALLS` opens the first gap and `count_status` the second. The counted rule is strict — `disputed` is excluded alongside `not_counted` — which is what makes *both* of the Archives' printed 1868 totals rows reproducible, 294 as cast and 285 as counted, where D044 could only pick one. It is derived by **two rules**: state rows take the row rule, while an `is_total` row takes the sum over its year's state rows, since aggregates are never flagged and the row rule would hand back the cast value. `president_electoral_rank` and `took_office` are computed from the counted measure, because who won is settled by the votes Congress counted. Both measures, the status and its reason reach the **public API** as of #139/D048 — `count_status` and `count_status_reason` were appended to `EC_PV_COLUMNS` there, joining the pair D047 had already added).

### `db_tools.py` — `DBC` class

Thin psycopg2 wrapper (schema/table create/drop, `insert_df_into_table` via `execute_values`, `select_query_to_df`). Constructor exits the process on connection failure. This is the only importable module; the notebooks depend on it.

### Publishing (`posts/`, `social/`, `tooling/`) — a second, non-pipeline workstream

The repo has a **writing** side that shares nothing with the data pipeline except its subject, and it has its own conventions and CI gates. Findings are published as the **"Counted, Not Assumed"** blog series, live at <https://frederick-douglas-pearce.github.io/blog/>.

- **[`posts/`](posts/) is tracked and holds published posts only**; its [README](posts/README.md) is the authoritative spec for frontmatter, share cards, the Prettier gate, and the publish path. Read it before touching anything under `posts/`.
- **`social/` is git-ignored working state** — drafts, the candidate ledger, the series outline. Deliberate: a half-finished post about a claim that turns out to be wrong should not be in a public repo's history. Two exceptions are tracked: `social/images/` (rendered OG cards plus their committable TOML briefs) and the published post itself, which moves to `posts/`.
- **`tooling/`** holds the three publishing scripts: `publish-to-pages.py` (frontmatter transform + OG resolution + content-compare, syncing to a separate Jekyll Pages repo), `check-og-cards.py` (the PR guard, which reuses the publisher's own `build_plan` rather than re-deriving its rules), and `render-og-card.py` (1200×630 cards from a TOML brief).
- **Three of the five CI workflows are publishing gates**, not pipeline CI: `pages-sync.yml` (cross-repo push on merge to `main`), `og-card-guard.yml`, and `prettier.yml`. The Prettier gate covers **`posts/` only** and pins the *exact* versions the Pages site pins — caret ranges would let it drift a version away from the site's, which is the one way it can pass here and fail there.
- **Two editorial guardrails are absolute.** Nothing critical of a data source is ever published (findings about the National Archives, MIT Election Lab, or UCSB go to them privately via the ledger's `outreach` lane) — and every historical claim is checked before publishing. Both are enforced by review, not by CI.
- **The `marketer` agent drafts public-facing copy; the parent agent handles anything landing in the repo itself** (README, commit messages, PR bodies). Keep that split — it is in the agent's own definition. Agent output is saved verbatim as `social/drafts/<date>-<slug>.raw.md` alongside the edited version, because the raw-vs-shipped diff is what calibrates the agent.

## Working conventions

- **Validation is inline and load-bearing.** The notebook is dense with assertion-style checks (`Q: ... A: {len(x) == len(y)}`, `value_counts`, grain checks like "one row per candidate"). When editing transform logic, preserve or update these — they are how the pipeline catches scrape/parse regressions.
- **Hardcoded data corrections.** Real historical anomalies are patched by name: 2016 "Other" candidates (electoral votes and names collected manually from the Archives Notes section), 2000 DC abstainer, name mismatches between Table 1 and Table 2 (e.g. "Bob Dole"→"Robert Dole", Donald Trump's middle initial, "Faith Spotted Eagle" name split). In the `usvote` package each lives as a provenance-carrying constant in `src/usvote/transform.py` paired with an `apply_*`/reconcile function and a test in `tests/test_transform.py`; [`docs/corrections.md`](docs/corrections.md) is the browsable catalog. Expect similar per-election special-casing when extending coverage; add a new anomaly the same way (constant + test + catalog row), documenting its source as existing entries do.
- **NaN → None** is handled at the DB write boundary (`usvote.db.insert_df_into_table` via `_df_to_sql_rows`), which maps any null-like value to SQL `NULL` and unboxes numpy scalars. Transform frames may carry pandas NA (esp. `StringDtype`, whose NA is `NaN`); do **not** rely on an upstream `applymap`/`.map` NaN→None pass — it silently no-ops on `StringDtype` columns (the notebook's approach), which is why the conversion lives at the single write chokepoint.
- Git workflow is PR-per-feature-branch merged to `main` (`feature/<topic>` naming).
