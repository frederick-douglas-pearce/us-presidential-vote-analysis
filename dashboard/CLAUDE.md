# CLAUDE.md — `dashboard/`

Module-specific guidance, moved from the root `CLAUDE.md` (#298). Claude Code loads this file on demand, once a file under this directory is read. The root file's module map and cross-cutting invariants still apply.

## Overview

**The public dashboard (E9, #275)** is the front end of D001's what-if explorer, re-scoped from the analytical mart by [D070](../.claude/specs/decisions.md). It is **live at `https://explore.us-presidential-election-center.org`** and **reads the live public `/v1` API**, bundling no copy of the data — so D030 holds structurally and the API is its own first consumer. Its runtime code references no `run.app` URL and imports nothing from `usvote` (D070(b)). New data shapes are built only when a named chart needs them, as a new snapshot table or `/v1` endpoint, never a Postgres mart object (D070(c)). **The platform is Plotly Dash on App Engine standard** ([D071](../.claude/specs/decisions.md), the verdict of the research spike #276): one pinned F1 instance in a GCP project of its own, `uspv-explore`, whose budget and kill-switch cannot pause the API (#283). Its code lives in this repo under `dashboard/`, outside the `usvote` package — see [`dashboard/`](#dashboard--the-public-dashboard-e9) below. The spec, including every story body and the constraints each one carries, is [`.claude/specs/backlog-dashboard.md`](../.claude/specs/backlog-dashboard.md).

## Deployment

**The dashboard deploys separately (E9-S2, #277 / D071).** [`.github/workflows/deploy-dashboard.yml`](../.github/workflows/deploy-dashboard.yml) is `workflow_dispatch`-only, waits on the same `production` environment gate as the API deploy, and authenticates by keyless WIF into `uspv-explore` through a pool in that project, so nothing about the API's deploy identity can reach it. It exports `dashboard/requirements.txt` from `uv.lock` (the `dashboard` group only, `--no-emit-project`, so the deployed runtime has no `usvote` to import), deploys a new version **without promoting it**, probes it on its own version host, moves traffic, probes `explore.`, and only then deletes every other version — `min_instances`/`max_instances` are per-version settings, so a leftover version keeps its own pinned instance running. A failure before that cleanup moves traffic back to the previous version automatically. Runbook: [`docs/deploy-dashboard.md`](../docs/deploy-dashboard.md) (the project, budget and runtime service account, WIF, the domain, rollback, monitoring, and the cold-start and load measurements). The domain is a **DNS-only CNAME** with App Engine's managed certificate — unlike the API, it is not proxied through Cloudflare (D071(c)): the zone holds only the Search Console TXT record that verifies the apex and a grey-cloud CNAME from `explore.` to `ghs.googlehosted.com`, and the zone's "Always use HTTPS" setting the API sits under is left untouched (runbook §8). So there is no Worker, edge cache, rate limit or origin secret in front of the dashboard, and the **residual exposure** is egress: abuse could run it up before the budget's alerts, which lag by hours, fire the kill-switch — one of D071's flip conditions (runbook §11). Cloudflare *is* on the dashboard's data path, since every read goes to `api.` through the API's Worker and edge cache; `explore/api.py` depends on that in one place, stripping the `W/` prefix Cloudflare adds to the strong `ETag` when it compresses (`etag_version`). The budget kill-switch in `deploy/killswitch/` gained an App Engine target in #283 (`KILLSWITCH_TARGET=app_engine` sets the app `USER_DISABLED`; never `max_instances: 0`, which App Engine reads as no cap), and the daily `api-canary.yml` probes `explore.` beside the API.

### `dashboard/` — the public dashboard (E9)

A Plotly Dash app (D071) that is **not part of the `usvote` package** and imports nothing from it (D070(b)). `dashboard/` is the App Engine **deploy root**: `app.yaml` (one pinned F1 instance with warmup, one gunicorn worker so one process and one cache, the least-privilege runtime service account, no `env_variables`) and a `.gcloudignore` **allow-list** that uploads only `app.yaml`, the exported `requirements.txt` and the app package, so nothing new under `dashboard/` ships by accident. The package is `dashboard/explore/`:

- `config.py` — the API base and the canonical host, as **constants**. Neither is configurable, because a base URL supplied by configuration is a second data input that no source-text guard can see.
- `api.py` — the dashboard's only way to read data. `fetch` is the **one outbound chokepoint**: `/v1/` paths only, built on the fixed base, scheme and host checked before opening, no redirects followed and no proxy variables honored. Behind it sits an in-process cache keyed on `snapshot_version` (each response's `ETag` is the snapshot's content hash), refilled by one daemon refresher thread that prefetches every registered path and swaps the cache whole; fills pass a token bucket kept under the API's per-IP rate limit (D071(d)). D072 sets the MVP prefetch extent to `/v1/meta` and `/v1/elections`, with a year filled on a miss; the landing page registers `/v1/meta`, and both elections pages and both state pages `/v1/elections` (#306, #307, #279; the refresher fills a path once however many pages register it), and `TestCache.test_the_process_client_prefetches_what_pages_register` (`test_dashboard_app.py`) pins that set. **Pages read only through `CLIENT.view()`** (#305), which pins one snapshot for the whole render: a miss whose response names another version raises `ApiUnavailable` (the page shows its degraded state) rather than mixing versions, and wakes the refresher; so a page also stays degraded while the API edge serves a year path and `/v1/meta` at different versions, a window the deploy's edge purge closes (D072; #314 asks whether a stale entry can land after it). A render has one deadline, `MAX_REQUEST_WAIT_S`, shared by its wait for the first snapshot, its fill tokens and its fetches (each capped at `VISITOR_FETCH_TIMEOUT_S`, against the refresher's `FETCH_TIMEOUT_S`); a fill that would leave its fetch less than `MIN_USEFUL_FETCH_S` is refused before it takes a token. After a successful refresh a visitor's wake-up is never dropped but is answered at most once per `MIN_RECHECK_INTERVAL_S`; after a failed one the refresher backs off unwakeably. The refresher starts lazily, never at import, so importing the module makes no network call. **Coverage variables** (#279, D074): `COVERAGE_VARS` (`year_max`) is the closed set of names an `on_miss` template or a `validate` source may use besides a page's path variables; `coverage_vars` reads them from a `/v1/elections` body, accepting `year_max` only as the latest year that body serves, and never from a request. `ROSTER_PATH`, `/v1/elections/{year_max}`, is the state roster.
- `app.py` — the Dash app and its WSGI entry point (`explore.app:server`). It 301s the `appspot.com` host to `explore.`; names each page's URL from the page Dash's router matches (D073, #312): `resolve` asks `dash._pages._path_to_page`, and a matched path gets a canonical link built from the page's path template and its variables (no query string) and an `og:url` adding the query as the page's `query=` parser normalizes it, while a path no page matches, one a page's `validate=` rejects from the snapshot already in memory, one whose percent-escapes change it when decoded (`raw_path`: gunicorn's `RAW_URI` as sent, normalized to one leading slash as Werkzeug normalizes `request.path`, against the decoded path — Dash's router matches the browser's still-encoded `location.pathname`, so only a path with no effective escape is matched the same way on both sides; the runbook's §9 checks after a deploy that App Engine's front end passes the raw target through), or Dash's custom-404 module `not_found_404`, answers **404** with `noindex` and neither tag (a source not cached yet counts as matched, so the index never waits on the API). `og:url`'s query pairs are de-duplicated, so a repeated filter names the same URL as a single one. It rebuilds Dash's page card tags itself (`include_pages_meta=False`) without Dash's `twitter:url`, which is the raw request URL, and the index resolves once per request, so its status and tags always agree. The three Dash privates it uses are pinned in `TestDashPrivates`. It fills the cache synchronously on `/_ah/warmup`, and sets `suppress_callback_exceptions=True` so the index HTML carries no data and never waits on the API — which is what keeps a link preview's time to first byte short (D071(g)).
- `pages/` — Dash Pages. Shareable views are **paths**, so each one server-renders its own Open Graph card (D071(a)); the query string carries filters within a view. Each page declares in `dash.register_page` every API path it reads: `prefetch=(...)` for paths the refresher warms on every new snapshot version, `on_miss=(...)` for paths filled on a miss (templates of the page's path variables, e.g. `/v1/elections/{year}` for `/election/<year>`, or of the coverage variables, e.g. `/v1/elections/{year_max}`, D074), and `success=` the id of an element it renders only from a successful read. `TestRegistryCoverage` renders every page (templated ones at a concrete value) from recorded responses and fails an undeclared read or a missing marker, and `test_pages_read_only_through_a_render_scoped_view` (its rule is `client_misuses`, both in `tests/unit/test_dashboard_app.py`) fails a page that reaches `explore.api` other than through `CLIENT.view` (a module imported under another name, such as `from explore import api as x`, is not tracked). `TestRegistryCoverage` runs layouts only (the lint scans the whole page source, callbacks included): a page's callbacks that read the cache must be covered by the page's own tests. Two more keys, both optional (#312): a templated page registers `validate=(source, judge)` (`api.Validate`) — a source path that is a literal it lists in `prefetch`, or (D074, #279) one it declares in `on_miss`, a literal or a template over the coverage variables, and never one built from a path variable; and a pure, total `judge(path_vars, body) -> bool` (a judge that raises anyway is logged and refuses, at the index and at render, rather than answering 500) — and a page that reads filters registers `query=` its parser. **A templated page formats a path variable into an API path only after `api.accepted(view.get, VALIDATE, {...})` accepts the keyword arguments its layout received**, because Dash's router merges the query string over the path variables (`?year=..`, `?year=1&year=2`, `?year=`) and its routing request never passes through the index; a refused value renders the page's not-found state and never fills (with the source cold, at most one fill, of the source itself). Without it, `fetch` refuses a malformed path with `ValueError`, which the `except` in `pages/home.py`'s layout does not catch, and a junk year takes a fill token. `TestValidateBeforeFill` renders every registered templated page through the routing request at hostile values and fails one that fetches, takes a token, errors or renders its success marker; `TestRegistryContracts` fails a `validate` source the page neither prefetches nor declares in `on_miss`, or builds from a path variable, an `on_miss` placeholder that is neither a path nor a coverage variable, and a `query=` parser that is not total over hostile input, returns anything but `str` pairs, is not idempotent through re-encoding, or emits a key named after a path variable (the router would let that key override the path, and the page would render a different view than its canonical link names). A parser runs at index time, so it reads no API; a callable `title` or `description` is called by Dash with **unvalidated** path variables, at index time too, so it must be total and read no API.
- `components.py`, `labels.py` (#306), `query.py` (#307) and `export.py` (#309) — the pieces every table shares: pure functions of what a page already read (a response's provenance, a field name, a cell value), importing nothing from `explore` but each other, by name and without a cycle (`TestSharedPieces.test_the_shared_modules_read_no_api` and `test_the_shared_modules_import_each_other_without_a_cycle` in `test_dashboard_elections.py` check it). **Every table goes through `components.table`** (#309, D075), which builds its body and its CSV download from one row list: the file sits in the link's `data:` URL, built in the render, so a download makes no request and has no route or callback, and with no rows there is no table and no link. `export.py` writes it: a byte-order mark, a preamble of `#,<sentence>` rows (each source the table carries with its license, from the response's own `meta.provenance`; the snapshot version; the years each source covers; the view's URL with the filters the render applied; the table's notes; what an empty cell means), a blank row, the header of raw public field names (the displayed fields, then the keys `state_usps` / `candidate_slug` / `year` and the count reason where a table shows them only in a cell or not at all) and the rows. A null is an empty cell, text gets a `'` before a leading formula character, and the sources come from the columns through three disjoint field sets (`EC_FIELDS`, `POPULAR_VOTE_FIELDS`, `CENSUS_FIELDS`), so a new field must be placed in one. It writes RFC 4180 rows itself, because the guard bans `csv` and `io` from runtime modules. `components` holds the **provenance footer**, built from a response's own `provenance` (`/v1/meta`'s, or the `meta.provenance` every other response carries) and shown on every view that rendered data, and the degraded state, whose "isn't responding" wording `scripts/probe_dashboard.sh` greps. `labels` holds **the one label table**, `LABELS`, keyed by public `/v1` field name, never a snapshot column (`TestLabels.test_every_label_keys_a_public_api_field_never_a_snapshot_column` checks each key against `usvote.api.models`' field names and their `validation_alias`es); a later table adds rows to it rather than labeling inline. The table is flat, so a key means one thing everywhere, and a field name the API uses with two meanings needs a qualified key for the second: `candidate_count` already is one (a `/v1/elections` row's per-year count, against `/v1/meta`'s distinct candidates across the snapshot), and `coverage` is another: the plain key is a per-capita row's (#280), so the provenance block's year windows would need a qualified one. Each header carries its raw field name as a tooltip, and a "Column names" glossary under the table repeats them for touch screens. `has_popular_vote: false` reads "Not in this dataset", never "No". `labels` also holds the cells a null or a closed value can reach (#307): a label for each closed value of `pv_status` and `electoral_count_status` (tested against `usvote.pv.status` and `usvote.count_status`), the popular-vote null table (`popular_votes`, which takes the window from `coverage` and reads a year before, after or inside it differently), a null party with its reason (`party_cell`, the cell both of the one-election view's tables use), and the count-status cell with the Archives' reason verbatim. `query` holds URL-state syntax, because a page module cannot import another: the single-value rule, `encode_search` (the one normal form `og:url` and every filter callback write), the year, USPS and slug patterns, and the shared year range (#279): its keys and parse, `checked_year` (the one check of a year read from a body, which `api.coverage_vars`, `year_span`, the one-election view, the state history and the picker use; the elections index's rows are not yet checked, #334), a served span, and the bounds a render applies. `components` also holds the year-range slider every year-filtered table uses.
- `pages/election.py` — the one-election view, the election panel (#308), T2 and T3 (#307) and T6 (#280), at `/election/<year>`. The panel, T2 and T3 come from one `/v1/elections/{year}` response (its `election` block, `data` and `summary`) and T6, every state's persons per electoral vote, from `/v1/elections/{year}/per-capita`; both are filled on a miss in the same render, so a failed per-capita read degrades the whole page and the success marker covers the panel and all three tables. **The panel** (`election-panel`, first on the page and never filtered) lists who led under each method, whether the popular vote or the hybrid changes the winner, the three margins (in percentage points, as the API serves them), whether anyone won a majority of electors appointed, and `pv_coverage`, each label tooltipped with its field name, with the hybrid's one line of help text (`labels.HYBRID_NOTE`, under T3 too) and a glossary. Its cells come from `labels` (`winner`, `flip`, `margin`, `ec_majority`, `share_cell`): a null popular-vote or hybrid field outside the window (`labels.in_pv_window`, from `coverage`) reads "Not applicable: no popular vote in this dataset for this year", never "No"; inside it, and for the Electoral College fields at any year, a null names no cause; a value is shown whatever the year, as T2's popular votes are. `render` checks the window once with `query.year_span` before any cell reads it, whatever the `election` block holds. The `election` key is required; the API serves `election: null` on a build gap while the rows stay correct, so a null renders the panel's own sentence (`election-panel-unavailable`) and the tables, while any other shape, a block naming another year or a missing panel field degrades the page, as a malformed window does with or without a block. T3 adds `ec_share_hybrid` and `hybrid_score`; the score follows T3's own year rule (`has_popular_vote`, through the same `_national_pv` as the row's popular-vote cells), so a T3 row never disagrees with itself about the popular vote. T6 is narrowed only by the `state` filter, as T2 resolved it (never re-resolved against T6's rows), and says so under its heading. Its null cells come from `labels.persons_per_electoral_vote` and `labels.population`, the single statement of why a figure is null: no governing census figure (1848 Texas) before a zero allotment (1864, 1868); a null neither explains names no cause, and an unknown `coverage` renders as text, so neither degrades the page. The year is validated from the prefetched `/v1/elections` (`served_year`, never a literal), so an unserved year 404s at the index and renders the page's not-found state (`election-not-found`). T2's filters are `state` (USPS) and `candidate` (slug), the API's own names, and `pv_status` / `electoral_count_status`; a state or candidate absent that year falls back to "all", while a status is kept even when nothing matches. T3 is never filtered. Every state and summary row must name the validated year, or the body is malformed and the page degrades, as it does for an empty summary (a build regression to the API). Its popular-vote columns read the year's `has_popular_vote` from the index row the page already read, beside a year-level sentence from `coverage`. Opening a year makes two requests: the year, then its per-capita table (the index is prefetched, and a snapshot serves only once every prefetch filled).
- `pages/state.py` — the state history, T4 (#279), and T7, its persons per electoral vote (#280), at `/state/<usps>`, from `/v1/states/{usps}` and `/v1/states/{usps}/per-capita`, both filled on a miss in the same render (one rule, `_rows`, checks both bodies' rows). T7 is narrowed by the shared year range only. The code (upper case only) is validated against the roster `ROSTER_PATH`, filled on a miss and shared with `/states` (D074), so an unserved code renders `state-not-found`, fills nothing built from it, and 404s at the index once the roster is cached. Filters: the shared year range, judged against the dataset's span as on `/elections` (a range before the state's first election is an honest empty result, and the slider spans the dataset), `candidate` (slug) and `pv_status`. Every row must name the path's state and a year the index serves, or the page degrades. Each year links to `/election/<year>`; T2 links each state to `/state/<usps>`. Candidate links and the candidate history wait for a `/v1/candidates` index to validate against (#330, #331).
- `pages/states.py` — the state picker, `/states`: every state and DC from the roster, linked to its history; there is no second copy of the roster (D006). It and the state page's judge read the roster through one function, `api.roster`, so a body it refuses both refuse, and each also requires the rows to name the latest election (the picker from the index's coverage, the judge from the roster's own).
- `pages/elections.py` — the elections index, T1 (#306), and the pattern later tables follow. Each year links to its `/election/<year>`. **Paths:** a collection is plural (`/elections`), an item singular (`/election/<year>`, #307). **Filters live only in the query string**, read by the page's one `query=` parser, which the layout also calls, so `og:url` names exactly the view it opens. The parser is syntactic (it runs at index time, with no data); whether a value lies inside the served span is the layout's question, and a bad parameter falls back to that filter's default only, except that an inverted pair (compared as written, before the span check) drops both bounds. That is per parameter as `og:url` is: it drops only the syntactically bad parameters and keeps an out-of-span year, which the layout replaces with its default. A year range uses the keys `year_from` / `year_to` (the API's own names), shared across pages. Each table is `components.table` with a filename naming the view and the table (`elections.csv`, `election-<year>-by-state.csv`, `state-<usps>-history.csv`, …). A filter change is a pure callback that writes the normalized query (the same normal form as `og:url`, or `""`) to a page-local `dcc.Location(refresh="callback-nav")`, and leaves an unchanged one alone; Dash's Pages router then re-runs the layout from the cache, so a filter change makes no API request. Controls set no `persistence`, which would override the URL. A page module is executed by Dash before it is in `sys.modules`, so it cannot define a `dataclass` (use a `NamedTuple`), and tests reach it through its layout's `__globals__` (`pages.elections`) rather than importing a second copy.

**`tests/unit/test_dashboard_guards.py` is the only acceptance guard for D070(b)**, and its design matters because `usvote` *is* installed in the dev environment, so an import failing proves nothing. It runs the dashboard in a fresh interpreter whose `usvote` finder **records every attempt** and refuses it (catching `try: import usvote / except ImportError` and dynamic imports, which a `sys.modules` check would miss), installs an audit hook that records every socket host, and compares those hosts against an **independent literal** of the API host rather than against `explore.config`, so repointing the config fails the test instead of moving it. The same hook records `usvote` import events and every file opened: an open outside `LIBRARY_ROOTS`, `explore/` and `ALLOWED_FILES`, or anywhere under `tests/`, fails. It refuses SQLite connections and every socket creation, and a socket created by anything not in `ALLOWED_SOCKET_CREATORS` fails; each allow-list gives its reason per entry. Beside it: an AST lint against a second HTTP client, a file read or a dynamic import; no `run.app` anywhere in the dashboard or its deploy; no data files in the deploy root; the exact `app.yaml`; the `.gcloudignore` allow-list; the API image not gaining Dash; and the deploy workflow exporting exactly the `dashboard` group. It runs twice (#293): once with every connection refused, and once over a fake transport that answers the API host from recorded fixtures, so prefetching, every registered page's render and a fill on a miss all run under it. Each page's `success` marker is its contract there (#305): the success run requires it in every page's render, the refused run requires it in none. Templated pages render at `GUARD_PATH_VALUES` (`year`, `usps`), every `on_miss` template must resolve from those or a coverage variable or the run fails (#279), and the one-election view's render at 1824 makes the success run's first fills on a miss, `ELECTION_MISSES` (#307; a fake page the guard registered stood in before it), which the run asserts by name: some registered page's `on_miss` reads `MISS_PATH`. The success run also renders `/election/1825` and asserts the page's not-found state, neither its success marker nor the degraded state, with no request reaching the transport (`REQUESTED` records every request, answered from a fixture or not); `ELECTION_MISSES` adds `/v1/elections/1824/per-capita` after `MISS_PATH` (#280); `/state/GA` adds the roster, `/v1/states/GA` and `/v1/states/GA/per-capita` fills (`STATE_MISSES`), and `/state/ZZ` then renders `state-not-found` with no request. The #312 machinery tests in `test_dashboard_app.py` use their own fake page at `/fake-election/<year>`; their `register` fixture refuses a fake page that shares any URL with a registered page, checked by route both ways (the fake's own path routes nowhere, and no registered page's concrete path matches the fake's template), since Dash's router takes the first match. **A page that registers a new prefetch path adds its recorded response to `FIXTURE_FILES`** in that test, or the success run fails. The success run also requires every table's download link (`DOWNLOAD_IDS`), so each CSV is built under the guard. Its stated limit: a file read in C that bypasses Python's `open` (other than SQLite's) is not seen. Dashboard tests may import the vocabulary modules `usvote.snapshot_schema` and `usvote.count_status`, which are stdlib-only, `usvote.pv.status`, which is not. The label-key check also imports `usvote.api.models`, which is not a vocabulary module: its package `__init__` imports `usvote.api.app` (the `create_app` factory, never called) and with it FastAPI, though it builds no app.
