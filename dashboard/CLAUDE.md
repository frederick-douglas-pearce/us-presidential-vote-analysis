# CLAUDE.md — `dashboard/`

Module-specific guidance, moved from the root `CLAUDE.md` (#298). Claude Code loads this file on demand, once a file under this directory is read. The root file's module map and cross-cutting invariants still apply.

## Overview

**The public dashboard (E9, #275)** is the front end of D001's what-if explorer, re-scoped from the analytical mart by [D070](../.claude/specs/decisions.md). It is **live at `https://explore.us-presidential-election-center.org`** and **reads the live public `/v1` API**, bundling no copy of the data — so D030 holds structurally and the API is its own first consumer. Its runtime code references no `run.app` URL and imports nothing from `usvote` (D070(b)). New data shapes are built only when a named chart needs them, as a new snapshot table or `/v1` endpoint, never a Postgres mart object (D070(c)). **The platform is Plotly Dash on App Engine standard** ([D071](../.claude/specs/decisions.md), the verdict of the research spike #276): one pinned F1 instance in a GCP project of its own, `uspv-explore`, whose budget and kill-switch cannot pause the API (#283). Its code lives in this repo under `dashboard/`, outside the `usvote` package — see [`dashboard/`](#dashboard--the-public-dashboard-e9) below. The spec, including every story body and the constraints each one carries, is [`.claude/specs/backlog-dashboard.md`](../.claude/specs/backlog-dashboard.md).

## Deployment

**The dashboard deploys separately (E9-S2, #277 / D071).** [`.github/workflows/deploy-dashboard.yml`](../.github/workflows/deploy-dashboard.yml) is `workflow_dispatch`-only, waits on the same `production` environment gate as the API deploy, and authenticates by keyless WIF into `uspv-explore` through a pool in that project, so nothing about the API's deploy identity can reach it. It exports `dashboard/requirements.txt` from `uv.lock` (the `dashboard` group only, `--no-emit-project`, so the deployed runtime has no `usvote` to import), deploys a new version **without promoting it**, probes it on its own version host, moves traffic, probes `explore.`, and only then deletes every other version — `min_instances`/`max_instances` are per-version settings, so a leftover version keeps its own pinned instance running. A failure before that cleanup moves traffic back to the previous version automatically. Runbook: [`docs/deploy-dashboard.md`](../docs/deploy-dashboard.md) (the project, budget and runtime service account, WIF, the domain, rollback, monitoring, and the cold-start and load measurements). The domain is a **DNS-only CNAME** with App Engine's managed certificate — unlike the API, it is not proxied through Cloudflare (D071(c)): the zone holds only the Search Console TXT record that verifies the apex and a grey-cloud CNAME from `explore.` to `ghs.googlehosted.com`, and the zone's "Always use HTTPS" setting the API sits under is left untouched (runbook §8). So there is no Worker, edge cache, rate limit or origin secret in front of the dashboard, and the **residual exposure** is egress: abuse could run it up before the budget's alerts, which lag by hours, fire the kill-switch — one of D071's flip conditions (runbook §11). Cloudflare *is* on the dashboard's data path, since every read goes to `api.` through the API's Worker and edge cache; `explore/api.py` depends on that in one place, stripping the `W/` prefix Cloudflare adds to the strong `ETag` when it compresses (`etag_version`). The budget kill-switch in `deploy/killswitch/` gained an App Engine target in #283 (`KILLSWITCH_TARGET=app_engine` sets the app `USER_DISABLED`; never `max_instances: 0`, which App Engine reads as no cap), and the daily `api-canary.yml` probes `explore.` beside the API.

### `dashboard/` — the public dashboard (E9)

A Plotly Dash app (D071) that is **not part of the `usvote` package** and imports nothing from it (D070(b)). `dashboard/` is the App Engine **deploy root**: `app.yaml` (one pinned F1 instance with warmup, one gunicorn worker so one process and one cache, the least-privilege runtime service account, no `env_variables`) and a `.gcloudignore` **allow-list** that uploads only `app.yaml`, the exported `requirements.txt` and the app package, so nothing new under `dashboard/` ships by accident. The package is `dashboard/explore/`:

- `config.py` — the API base and the canonical host, as **constants**. Neither is configurable, because a base URL supplied by configuration is a second data input that no source-text guard can see.
- `api.py` — the dashboard's only way to read data. `fetch` is the **one outbound chokepoint**: `/v1/` paths and the one literal `HEALTH_PATH` (`/health`, D076), built on the fixed base, scheme and host checked before opening, no redirects followed and no proxy variables honored. Behind it sits an in-process cache keyed on `snapshot_version` (each response's `ETag` is the snapshot's content hash), refilled by one daemon refresher thread that prefetches every registered path and swaps the cache whole; fills pass a token bucket kept under the API's per-IP rate limit (D071(d)). D072 sets the MVP prefetch extent to `/v1/meta` and `/v1/elections`, with a year filled on a miss; the landing page registers `/v1/meta`, and both elections pages, both state pages and the candidate history `/v1/elections` (#306, #307, #279, #331; the refresher fills a path once however many pages register it), and `TestCache.test_the_process_client_prefetches_what_pages_register` (`test_dashboard_app.py`) pins that set. **Pages read only through `CLIENT.view()`** (#305), which pins one snapshot for the whole render: a miss whose response names another version raises `ApiUnavailable` (the page shows its degraded state) rather than mixing versions, and wakes the refresher; so a page also stays degraded while the API edge serves a year path and `/v1/meta` at different versions, a window the deploy's edge purge closes (D072; #314 asks whether a stale entry can land after it). A render has one deadline, `MAX_REQUEST_WAIT_S`, shared by its wait for the first snapshot, its fill tokens and its fetches (each capped at `VISITOR_FETCH_TIMEOUT_S`, against the refresher's `FETCH_TIMEOUT_S`); a fill that would leave its fetch less than `MIN_USEFUL_FETCH_S` is refused before it takes a token. After a successful refresh a visitor's wake-up is never dropped but is answered at most once per `MIN_RECHECK_INTERVAL_S`; after a failed one the refresher backs off unwakeably. **The keep-warm ping** (#346, D076): after every refresh attempt, succeeded or failed, the refresher GETs `/health` if one `REFRESH_TTL_S` has passed since the last ping *started* (stamped at the start, success or failure), so the Cloud Run origin does not scale to zero while the dashboard runs. It takes no bucket token, logs `api ping /health <elapsed>s` (a warning when the API is unavailable; any other error is a bug, logged at error level with its traceback) and never `api fetch`, discards its body (`/health` names the origin's snapshot version, never the cache's), and never counts as a failed cycle. Once a ping has been attempted, the wait after a successful cycle also ends when the next ping is due, so the worst gap between pings is, best effort, one TTL plus one unwakeable 30 s wait plus one full refresh (about 6 min); that ping-due cycle refreshes too and is not held to `MIN_RECHECK_INTERVAL_S`. Warmup, `refresh()` and visitors never ping, and a refresher that starts with a snapshot already serving waits one TTL first, so the guard's success run never pings. No page can read `/health`: `_fill` and `_visitor_fill` refuse it (`_refuse_health`), `test_only_api_names_the_keep_warm_path` (`test_dashboard_guards.py`) keeps the literal out of every other runtime module, and `test_only_the_refresher_cycle_calls_the_ping` makes `Client._cycle` the one place any runtime module refers to `_ping` (who calls `_cycle` is not checked; `TestKeepWarm.test_warmup_never_pings` and `test_a_visitors_miss_never_pings` cover today's request paths); `TestKeepWarm` drives the real `_run` on a fake clock. The refresher starts lazily, never at import, so importing the module makes no network call. **Coverage variables** (#279, D074): `COVERAGE_VARS` (`year_max`) is the closed set of names an `on_miss` template or a `validate` source may use besides a page's path variables; `coverage_vars` reads them from a `/v1/elections` body, accepting `year_max` only as the latest year that body serves, and never from a request. `ROSTER_PATH`, `/v1/elections/{year_max}`, is the state roster. `CANDIDATES_PATH`, `/v1/candidates` (#330), is the candidate index: the candidate history's `validate` source, a literal declared in `on_miss` (D074(ii)) and filled on a miss, so D072's prefetch extent is unchanged.
- `app.py` — the Dash app and its WSGI entry point (`explore.app:server`). It 301s the `appspot.com` host to `explore.`; names each page's URL from the page Dash's router matches (D073, #312): `resolve` asks `dash._pages._path_to_page`, and a matched path gets a canonical link built from the page's path template and its variables (no query string) and an `og:url` adding the query as the page's `query=` parser normalizes it, while a path no page matches, one a page's `validate=` rejects from the snapshot already in memory, or Dash's custom-404 module `not_found_404`, answers **404** with `noindex` and neither tag (a source not cached yet counts as matched, so the index never waits on the API). **A path is matched decoded once, as Dash's router matches it** (Dash 4.5.0, D089, amending D073): the router matches `app.router_key(pathname)` (`unquote`, then its strip), and the index `request.path`, which gunicorn has already decoded and which is never decoded again, so a percent-encoded link gets what the link it spells gets (`/election/18%32%34` is 1824, with `/election/1824` as its canonical link); `DECODED_PATHS` (`test_dashboard_app.py`) is the one table of pathname, key and path variable the router (observed in a real routing request), the hook and the index answer to, and the runbook's §9 checks after a deploy that nothing in front of the app decodes the path first. `og:url`'s query pairs are de-duplicated, so a repeated filter names the same URL as a single one. It builds the page card tags itself (`include_pages_meta=False`; `card_tags`, Dash's set without its `twitter:url`, which is the raw request URL, and never through Dash's `_page_meta_tags`, which would call the registry's title and read the snapshot again), and the index resolves once per request, so its status, tags and title always agree. **A title names a value only once it is checked** (#325, D083): `resolve` also returns the title and description, which the index writes as the card tags and, HTML-escaped (Dash interpolates it raw), as `<title>`. A value the page's `validate` refuses gets the page's `not_found=` heading followed by the site title, and its sentence as the description; a value whose source is not cached yet gets the page's title called with no variables, which names no value; an unmatched path and the custom-404 module get the custom-404 page's (`pages/not_found_404.py`, `NOT_FOUND_PAGE`), and a percent-encoded path the title of the path it spells (D089). Dash's client router sets the browser tab from the registry's `title`, called after the layout in the same request, so `follow_validation` wraps every validated page's registry `title` at import to judge from the snapshot in memory by the same helper (`checked`), never filling; a layout's fill on a miss lands first, so a cold refused value reads as not found too. `TestNotFoundTitle` checks each validated page's index, card, tab and heading agree with its source cached, and with it cold for each page whose source is filled on a miss; before the first snapshot it checks every validated page's index and registry title name no value; and `TestDashPrivates` pins the router's reliance. **The path's value wins** (#326, D081): Dash's router merges the query string over a page's path variables, so its `before_request` hook rewrites the Pages routing request first, dropping from the `search` input every key named after a path variable of the page the `pathname` input matches, decoded as the router decodes it (`strip_path_variables` on `router_key`, D089; a pathname the router's strip refuses is left for Dash), reading keys as the router's `parse_qs` does, so a render always matches its canonical link. **A content-encoded callback request is refused** (#456, D089): Dash 4.5.0 decompresses a gzip callback body the hook cannot read, so `refuse_encoded_dispatch` answers 415 (Werkzeug's default body) to a POST to the dispatch endpoint with any `Content-Encoding` but identity before Dash reads it (no callback sets `compress_payload`); `TestEncodedDispatch` pins it with a control that shows the bypass with the refusal off. **Dash's MCP server is off** (`enable_mcp=False`, which beats `DASH_MCP_ENABLED`; D089): it would run callbacks through a route of its own the hook never sees. The hook is gated on the dispatch endpoint and the router's `output`, reads the two inputs by position, and writes into the body Werkzeug caches, which is the object Dash's `get_json()` returns.
