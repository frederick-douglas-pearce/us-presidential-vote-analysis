# CLAUDE.md — `dashboard/`

Module-specific guidance, moved from the root `CLAUDE.md` (#298). Claude Code loads this file on demand, once a file under this directory is read. The root file's module map and cross-cutting invariants still apply.

## Overview

**The public dashboard (E9, #275)** is the front end of D001's what-if explorer, re-scoped from the analytical mart by [D070](../.claude/specs/decisions.md). It is **live at `https://explore.us-presidential-election-center.org`** (so far the walking skeleton from #277, with no tables yet) and **reads the live public `/v1` API**, bundling no copy of the data — so D030 holds structurally and the API is its own first consumer. Its runtime code references no `run.app` URL and imports nothing from `usvote` (D070(b)). New data shapes are built only when a named chart needs them, as a new snapshot table or `/v1` endpoint, never a Postgres mart object (D070(c)). **The platform is Plotly Dash on App Engine standard** ([D071](../.claude/specs/decisions.md), the verdict of the research spike #276): one pinned F1 instance in a GCP project of its own, `uspv-explore`, whose budget and kill-switch cannot pause the API (#283). Its code lives in this repo under `dashboard/`, outside the `usvote` package — see [`dashboard/`](#dashboard--the-public-dashboard-e9) below. The spec, including every story body and the constraints each one carries, is [`.claude/specs/backlog-dashboard.md`](../.claude/specs/backlog-dashboard.md).

## Tests

The dashboard's tests sit in the same tree: `tests/unit/test_dashboard_app.py` (behaviour,
offline through a fake fetch) and `tests/unit/test_dashboard_guards.py` (the structural
guards described under [`dashboard/`](#dashboard--the-public-dashboard-e9)). pytest's
`pythonpath` includes `dashboard`, so they import the `explore` package directly.
`tests/fixtures/dashboard/v1_meta.json` is a recorded public API response: test input
only, on the `ec_state_roster_by_year.json` precedent in the root [`CLAUDE.md`](../CLAUDE.md), and a guard asserts that no
runtime module names it.

## Deployment

**The dashboard deploys separately (E9-S2, #277 / D071).** [`.github/workflows/deploy-dashboard.yml`](../.github/workflows/deploy-dashboard.yml) is `workflow_dispatch`-only, waits on the same `production` environment gate as the API deploy, and authenticates by keyless WIF into `uspv-explore` through a pool in that project, so nothing about the API's deploy identity can reach it. It exports `dashboard/requirements.txt` from `uv.lock` (the `dashboard` group only, `--no-emit-project`, so the deployed runtime has no `usvote` to import), deploys a new version **without promoting it**, probes it on its own version host, moves traffic, probes `explore.`, and only then deletes every other version — `min_instances`/`max_instances` are per-version settings, so a leftover version keeps its own pinned instance running. A failure before that cleanup moves traffic back to the previous version automatically. Runbook: [`docs/deploy-dashboard.md`](../docs/deploy-dashboard.md) (the project, budget and runtime service account, WIF, the domain, rollback, monitoring, and the cold-start and load measurements). The domain is a **DNS-only CNAME** with App Engine's managed certificate — unlike the API, it is not proxied through Cloudflare (D071(c)): the zone holds only the Search Console TXT record that verifies the apex and a grey-cloud CNAME from `explore.` to `ghs.googlehosted.com`, and the zone's "Always use HTTPS" setting the API sits under is left untouched (runbook §8). So there is no Worker, edge cache, rate limit or origin secret in front of the dashboard, and the **residual exposure** is egress: abuse could run it up before the budget's alerts, which lag by hours, fire the kill-switch — one of D071's flip conditions (runbook §11). Cloudflare *is* on the dashboard's data path, since every read goes to `api.` through the API's Worker and edge cache; `explore/api.py` depends on that in one place, stripping the `W/` prefix Cloudflare adds to the strong `ETag` when it compresses (`etag_version`). The budget kill-switch in `deploy/killswitch/` gained an App Engine target in #283 (`KILLSWITCH_TARGET=app_engine` sets the app `USER_DISABLED`; never `max_instances: 0`, which App Engine reads as no cap), and the daily `api-canary.yml` probes `explore.` beside the API.

### `dashboard/` — the public dashboard (E9)

A Plotly Dash app (D071) that is **not part of the `usvote` package** and imports nothing from it (D070(b)). `dashboard/` is the App Engine **deploy root**: `app.yaml` (one pinned F1 instance with warmup, one gunicorn worker so one process and one cache, the least-privilege runtime service account, no `env_variables`) and a `.gcloudignore` **allow-list** that uploads only `app.yaml`, the exported `requirements.txt` and the app package, so nothing new under `dashboard/` ships by accident. The package is `dashboard/explore/`:

- `config.py` — the API base and the canonical host, as **constants**. Neither is configurable, because a base URL supplied by configuration is a second data input that no source-text guard can see.
- `api.py` — the dashboard's only way to read data. `fetch` is the **one outbound chokepoint**: `/v1/` paths only, built on the fixed base, scheme and host checked before opening, no redirects followed and no proxy variables honoured. Behind it sits an in-process cache keyed on `snapshot_version` (each response's `ETag` is the snapshot's content hash), refilled by one daemon refresher thread that prefetches every registered path and swaps the cache whole; fills pass a token bucket kept under the API's per-IP rate limit (D071(d)). D072 sets the MVP prefetch extent to `/v1/meta` and `/v1/elections`, with a year filled on a miss; today only `/v1/meta` is registered, and #306 registers `/v1/elections` with the first page that reads it. **Pages read only through `CLIENT.view()`** (#305), which pins one snapshot for the whole render: a miss whose response names another version raises `ApiUnavailable` (the page shows its degraded state) rather than mixing versions, and wakes the refresher; so a page also stays degraded while the API edge serves a year path and `/v1/meta` at different versions, a window the deploy's edge purge closes (D072; #314 asks whether a stale entry can land after it). A render has one deadline, `MAX_REQUEST_WAIT_S`, shared by its wait for the first snapshot, its fill tokens and its fetches (each capped at `VISITOR_FETCH_TIMEOUT_S`, against the refresher's `FETCH_TIMEOUT_S`); a fill that would leave its fetch less than `MIN_USEFUL_FETCH_S` is refused before it takes a token. After a successful refresh a visitor's wake-up is never dropped but is answered at most once per `MIN_RECHECK_INTERVAL_S`; after a failed one the refresher backs off unwakeably. The refresher starts lazily, never at import, so importing the module makes no network call.
- `app.py` — the Dash app and its WSGI entry point (`explore.app:server`). It 301s the `appspot.com` host to `explore.`, puts a canonical link and `og:url` on every page, fills the cache synchronously on `/_ah/warmup`, and sets `suppress_callback_exceptions=True` so the index HTML carries no data and never waits on the API — which is what keeps a link preview's time to first byte short (D071(g)).
- `pages/` — Dash Pages. Shareable views are **paths**, so each one server-renders its own Open Graph card (D071(a)); the query string carries filters within a view. Each page declares in `dash.register_page` every API path it reads: `prefetch=(...)` for paths the refresher warms on every new snapshot version, `on_miss=(...)` for paths filled on a miss (templates of the page's path variables for a templated page, e.g. `/v1/elections/{year}` for `/election/<year>`), and `success=` the id of an element it renders only from a successful read. `TestRegistryCoverage` renders every page (templated ones at a concrete value) from recorded responses and fails an undeclared read or a missing marker, and `test_pages_read_only_through_a_render_scoped_view` (its rule is `client_misuses`, both in `tests/unit/test_dashboard_app.py`) fails a page that reaches `explore.api` other than through `CLIENT.view`. That test runs layouts only: a page's callbacks that read the cache must be covered by the page's own tests. A templated page formats a path variable into an API path only after validating it (#312, item 6): `fetch` refuses a malformed path with `ValueError`, which the `except` in `pages/home.py`'s layout, the pattern pages copy, does not catch.

**`tests/unit/test_dashboard_guards.py` is the only acceptance guard for D070(b)**, and its design matters because `usvote` *is* installed in the dev environment, so an import failing proves nothing. It runs the dashboard in a fresh interpreter whose `usvote` finder **records every attempt** and refuses it (catching `try: import usvote / except ImportError` and dynamic imports, which a `sys.modules` check would miss), installs an audit hook that records every socket host, and compares those hosts against an **independent literal** of the API host rather than against `explore.config`, so repointing the config fails the test instead of moving it. The same hook records `usvote` import events and every file opened: an open outside `LIBRARY_ROOTS`, `explore/` and `ALLOWED_FILES`, or anywhere under `tests/`, fails. It refuses SQLite connections and every socket creation, and a socket created by anything not in `ALLOWED_SOCKET_CREATORS` fails; each allow-list gives its reason per entry. Beside it: an AST lint against a second HTTP client, a file read or a dynamic import; no `run.app` anywhere in the dashboard or its deploy; no data files in the deploy root; the exact `app.yaml`; the `.gcloudignore` allow-list; the API image not gaining Dash; and the deploy workflow exporting exactly the `dashboard` group. It runs twice (#293): once with every connection refused, and once over a fake transport that answers the API host from recorded fixtures, so prefetching, every registered page's render and a fill on a miss all run under it. Each page's `success` marker is its contract there (#305): the success run requires it in every page's render, the refused run requires it in none. Templated pages render at `GUARD_PATH_VALUES`, and a fake `/election/<year>` page's render at 1824 is the success run's fill on a miss, until #307 registers a real one. **A page that registers a new prefetch path adds its recorded response to `FIXTURE_FILES`** in that test, or the success run fails; #306, registering `/v1/elections`, also deletes the guard's `SYNTHETIC_PREFETCH`. Its stated limit: a file read in C that bypasses Python's `open` (other than SQLite's) is not seen. Dashboard tests may import the vocabulary modules `usvote.snapshot_schema` and `usvote.count_status`, which are stdlib-only, and `usvote.pv.status`, which is not.
